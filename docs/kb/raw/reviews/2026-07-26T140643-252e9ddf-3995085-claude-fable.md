## Review — ADR-0026 batched intents (docs-only diff, 1 file)

Fact-checked against the codebase: every file:line citation is accurate (`intentFixedBytes = 44` and the record layout at `engine/natsio/bus.go:26-42`, `onIntent` at bus.go:239, `ArrivedIntent` arrival-order/seq semantics at bus.go:137-143 and `engine/intent.go:65-71`, apply order `(grant desc, vehicle asc, controller asc, seq asc)` matches `engine/intent.go`, per-vehicle publish at driver.go:350, emergent claim sharding at driver.go:22-25). The math checks: 24 B header, (1 MiB − 24)/44 = 23,830 ≈ "~23.8k", 40k × 44 B = 1.76 MB. The 14.5k stress-dtla figure is real (14,537 at horizon, `docs/kb/articles/podcast-demo-workqueue.md:248`), and the caveat that BENCHMARKS.md's 1.36M msgs/s is fan-out delivery, not ingest, is correct (BENCHMARKS.md:75). The determinism story is sound: expansion before seq assignment preserves per-controller monotonicity, the record plane (`ts.{run}.log.intent`) is untouched, and cross-mode divergence is honestly scoped to statistical equivalence rather than CRC. The magic-bytes rejection rationale is correct — a v2 payload's leading `vehicle_id` can indeed spell `TSIB`.

**Blockers:** none.

**Should-fix**

1. **ADR-0026-batched-intents.md:56-59 — demux is unspecified for unknown `schema_version` values.** The spec covers absent/`2` ⇒ v2 and `3` ⇒ TSIB, but says nothing about `1`, `4+`, or non-numeric. If implementers fall through to v2 parsing, a future codec version against an old engine gets misparsed instead of dropped. One sentence ("any other value ⇒ drop + count, loud") closes it — cheap now, a migration note after M4 ratifies.

2. **ADR-0026-batched-intents.md:57 — `schema_version` header key is already used with a different meaning.** Engine-published messages stamp it with the *global* contract version (`SchemaVersion = 2`, `engine/natsio/server.go:79`; set at bus.go:283, contract.go:956, etc.). The ADR repurposes value `3` on the intent subject to mean "TSIB codec." The two currently coincide at 2, but if the global constant ever bumps to 3, a v2-format intent stamped with the global header parses as TSIB and is dropped (loudly, via magic/length check — but the intent is still lost). State explicitly that on `ctlIntent` the header value is the intent wire-format version and that global `SchemaVersion = 3` is reserved/skipped for this subject.

**Nit**

3. **ADR-0026-batched-intents.md:219-222 — "rejected structurally — loud, never silent" is stronger than the code guarantees.** A header-less single-record TSIB read as v2 passes `DecodeIntent`'s length check (bus.go:110) iff the bytes at record offset 16-17 (low accel-mantissa bytes) equal exactly 24; it then survives as a garbage-`vehicle_id` v2 intent and dies at claim filtering, not structural validation. Multi-record batches can't pass (routeLen would exceed 48). Astronomically unlikely, but the pinned M1 test only pins one payload; reword to name claim filtering as the backstop.

**Question**

4. ADR-0026-batched-intents.md:11 cites ADR-0006 §2 as "live-plane message discipline"; §2 is actually "Live messages are self-sufficient" (the 1 MiB discipline lives in bus.go:300's watermark convention, not a numbered ADR-0006 clause). TSIB batches remain self-sufficient, so the amendment is compatible either way — just confirm §2 is the intended anchor rather than §7 (binary SoA framing).

Design relative to the repo's own ADRs is solid: wire-codec-only batching keeps the ADR-0005 single-writer/drain model and replay guarantee intact, the route-exclusion rule correctly avoids competing same-vehicle intents under first-wins, and no-barrier is the right call to not smuggle scheduling semantics into a codec change.
