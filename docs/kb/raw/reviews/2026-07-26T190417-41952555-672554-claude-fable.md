## Findings

**Blockers:** none. The mechanism is sound: quiesce → sentinel → published-count watermark → re-quiesce, and the *trailing* `quietWindow()` (driver_test.go:1283) is what actually establishes the zero-outstanding invariant for measurement, so even a spoofed watermark can't corrupt the FIFO. `server.go` and `BENCHMARKS.md` changes are comment/doc-only — no subject or payload change, no ADR needed; the NATS per-publisher-ordering statement is accurate.

**Should-fix (comment precision, not mechanism):**

1. `driver_test.go:1242-1248` — the comment claims the delta "can ONLY be the sentinel's own response (an earlier slow response cannot satisfy it)". That's stronger than what's provable: `LastObsTick` is stored at the *top* of `onObs` (driver.go:342), before compute, so Phase A's "worked on" means "started processing". If a fleet-scale compute of the last warm-up obs outlasts the 50 ms quiet window (batch mode publishes nothing mid-compute — the comment two paragraphs up concedes exactly this), the first `quietWindow()` can pass mid-compute and the *warm-up* obs's response can then satisfy the ≥`vehicles` watermark instead of the sentinel's. Harmless — the trailing `quietWindow()` still catches the sentinel's late response (fresh restarts the window) and the measurement opens clean — but the "unspoofable" / "can ONLY be" wording overclaims. Either weaken the comment, or make it airtight by having Phase A wait for `LastObsTick` *and* a `SentIntents` delta covering the last warm-up obs. Comment-only; fine to defer per the triage bar.

**Nits:**

2. `driver_test.go:1230,1235,1238` — `quietWindow`'s failure messages ("never quiesced after warm-up", "intent buffer not empty at measurement start") are now emitted from two call sites; on the first call (pre-sentinel) "at measurement start" is wrong, on the second "after warm-up" is wrong. A misdirected message on a rare loud failure — cosmetic.

3. `driver_test.go:1265` — the watermark hangs the full 30 s if a driver-side `Publish` errors (`sentIntents` only increments on success, driver.go:405,419). Fails loud, so acceptable; noting for awareness only.

**Questions:** none — the "exactly `vehicles` intents" premise holds: fleet is stable on a ring (no despawns), `onObs` emits exactly one intent per claimed ego per obs, and `SentIntents` counts the same per-vehicle unit in both batch and batch-off modes (driver.go:280-283), so the watermark is mode-independent as required for the A/B legs.
