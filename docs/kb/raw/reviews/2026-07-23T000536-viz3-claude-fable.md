## Findings

### Blocker

**B1. All-coincident lanes now teleport vehicles to synthetic placeholder coordinates on imported networks** — `engine/geometry.go:105-112` (removed `shapeLen == 0` branch) + `engine/netfile.go:185-189`.

Before: a vehicle on an all-coincident-shape lane (the diff's own example, `i30677892_0_0` on I-280) projected to the correct point with a wrong (east) angle for a frame. After: `SetShape` dedups to 1 point and clears the shape, `Project` returns `ok=false`, and `SnapshotFrame` falls into the placeholder branch at `engine/natsio/frame.go:115-118` — which emits `(XOff+s, 3.5·lat)` in the synthetic M1 chain frame ("all in-code M1 lanes run +x"). On an import those coordinates are unrelated to the network's UTM local frame, so the wire position for that tick is garbage.

Reachable: vehicles do end ticks parked on junction-internal lanes (your own M13 KB note — "parked-overshoot … on sub-4 m internal lanes"; `engine/engine.go:388-411` re-processes a hop the same tick only when the successor has a lower lane index). Downstream the client makes it worse than the bug being fixed: the 250 ms lerp draws a streak to the bogus point and back, and the displacement-derived speed (`snapshots.ts:116`) spikes to thousands of m/s, which kicks the articulator. Minimal fix options: keep the single deduped point and restore the sit-on-point projection (right place, angle 0 — strictly better than placeholder), or make the frame placeholder use the lane's sole shape point when one exists. The `netfile.go:185` comment ("clears to the placeholder projection, not an error") reads as if this path were benign; on imports it isn't.

### Nits

- `viz/src/artic.ts:29` — `wrapPi` comment claims range `(−π, π]`; the implementation yields `[−π, π)` (`wrapPi(π) === −π`). Behavior fine, doc wrong.
- `viz/src/artic.ts:31` / `glyphs.ts:337-339` — `MAX_DT_S = 0.05` makes trailer convergence fps-dependent below 20 fps (the tractor jumps the full distance but the integrator gets clamped time). Clamping distance (`v·dt`) would be scale-correct. Too early to matter.
- `viz/src/glyphs.ts:339,366` — the "SDF" is a binary-alpha rect, not a distance field; edges get ~1 px falloff and `icon-halo-width: 1` (main.ts) has essentially no field to render into. Works for tint/rotate; the "room to fall off" comment overstates.
- `viz/src/vehicles.ts:112` — `diffTrailers` update predicate is position-only; angle rides along. Currently provably safe (trailer center is a function of the angle, so angle can't change with a frozen center beyond float epsilon), but the coupling deserves a one-line comment so a future refactor doesn't break it silently.
- `viz/index.html:208-218` — comment says "colors injected from theme.ts" but `#9fb2e8` and `rgba(46,91,255,0.4)` are CSS literals, contradicting theme.ts's single-source-of-truth charter.
- `viz/src/glyphs.ts:384-385`, `main.ts` — `GLYPHS[0]!`/`GLYPHS[1]!` index positionally while the table carries a `cls` field; `theme.test.ts` guards presence by cls, not order. A lookup-by-cls helper would remove the silent-reorder hazard.
- `engine/geometry.go:36` — dedup is exact-equality only; near-duplicate points (differing in the last decimal) would still yield a near-zero segment with a noise-direction tangent. I-280 data has exact dups, so fine today.
