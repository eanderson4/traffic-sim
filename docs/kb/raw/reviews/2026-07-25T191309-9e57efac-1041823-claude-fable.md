## Findings

### Blocker

**B1. `TMPDIR=/data/tmp` is never created — every demo start fails, the site never comes up.**
`deploy/k8s/deployment.yaml:491-492` sets `TMPDIR=/data/tmp` precisely so the engine child's JetStream store lands in the bounded emptyDir. But nothing creates that directory: the initContainer (`deployment.yaml:447-453`) only mkdirs `/data/networks/.geojson-cache`, and `deploy/docker-entrypoint.sh` doesn't mkdir anything. Demo children are spawned without `-store` (`engine/cmd/demosrv/main.go:289-301`), so `serve` falls into the default branch `os.MkdirTemp("", "ts-serve-js")` (`engine/cmd/serve/main.go:575-580`), which honors `$TMPDIR` but does **not** create it — `Mkdir` under a nonexistent parent returns ENOENT. Every spawn fails, autostart exhausts its 4 attempts, the pod sits "healthy" (`/api/status` stays 200) serving an idle menu, and every 6-hour CronJob restart reproduces the same failure. Fix is one line — `mkdir -p "${TMPDIR:-/tmp}"` in `docker-entrypoint.sh` before the `exec` (entrypoint, not initContainer, so the knob stays owned by the manifest that sets TMPDIR).

### Should-fix

**S1. Crashed/OOM-killed children leak JetStream store dirs into the emptyDir until eviction.**
`jetStreamStoreDir`'s cleanup only runs on clean exit (`engine/cmd/serve/main.go:570-574`); a SIGKILL'd child (the OOM path the README itself flags for LA) orphans a multi-GB `ts-serve-js*` dir in `/data/tmp`. Repeated operator-driven switches within one 6-h window accumulate toward the 12Gi `sizeLimit` (`deployment.yaml:528`), whose breach is pod *eviction* mid-run. Cheap mitigation: `rm -rf /data/tmp/ts-serve-js*` in the entrypoint mkdir line won't help across child restarts within one pod — better is demosrv-side or a documented operator note; at minimum note the failure mode in `deploy/README.md`'s Operating section.

### Nit

**N1.** `Dockerfile:48-59` — no `USER`; the image is root unless the manifest's `runAsNonRoot` is applied. `docker run` per the README's local-verify suggestion runs root. Adding `USER 1000` in the image makes the manifest constraint redundant instead of load-bearing.

**N2.** `deploy/k8s/deployment.yaml:443` — initContainer memory limit 512Mi for a recursive ~5 GB `gcloud storage cp`; gcloud's parallel composite handling can spike past that and OOM the init. Works-or-crashes-loudly, so nit, but verify once on a real pull.

**N3.** `deploy/README.md:124-127` — the sed pipe applies `cronjob.yaml` through the `:TAG` substitution though it contains no `:TAG`; harmless, but a reader may infer the CronJob is image-coupled. A comment either place would prevent that.

### Question

**Q1.** `deploy/k8s/cronjob.yaml:394` — `registry.k8s.io/kubectl:v1.35.5`: confirmed-available for that exact patch tag? A missing tag makes the restart CronJob fail silently-ish (3 failed-job history) and the site then *does* idle out after run completion — the exact failure this CronJob exists to prevent. Worth a one-time `docker manifest inspect` before relying on it.
