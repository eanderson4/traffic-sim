### **2. Determinism Risks**

*   **Good**: `engine/scenario/scenario.go:167:2`: The `Hash()` function is excellent and appears highly robust against determinism risks.
    1.  It correctly sorts all included file parts by their relative paths before hashing, eliminating dependency on filesystem order.
    2.  It frames each part's content with its relative path, preventing hash collisions if, for example, two different parts had identical content.
    3.  It relies on a canonical formatter for YAML files, which is the correct way to achieve hash stability across cosmetic code changes.

*   **Good**: `engine/scenario/scenario.go:429:2`: The use of `gopkg.in/yaml.v3` for the canonical formatter (`canonicalYAML`) is a load-bearing choice that correctly addresses a major determinism risk. `yaml.v3`'s default behavior of sorting map keys is essential for stable hashes of `vtypes` in demand files and any other maps. This fulfills the ADR's goal of diffable, content-addressable scenarios. The test `TestHashStableAcrossFormatting` correctly verifies this property.

*   **Question**: The ADR states ADR-0005 scopes out cross-architecture bit-exactness. Go's standard library for float-to-string conversion is generally stable but not guaranteed to be bit-identical across versions/architectures. While `scenario fmt` mitigates this by creating a canonical source file, is there a plan to lock down the float formatting further if cross-arch determinism becomes a requirement? For M11's scope, the current implementation is acceptable under ADR-0005's constraints.

### **3. Design Weaknesses (relative to ADR goals)**

*   **Good**: The design is well-aligned with the ADR's goals of diffability and content addressing. The `scenario fmt` command and the robust `Hash()` implementation are direct and effective solutions. The addendum in ADR-0012, which narrows M11's scope to a base loader without overlays, is clearly met.

*   **Should-fix**: `engine/scenario/scenario.go:132:2`: The loader assumes the network file is JSON via a hardcoded `json.Unmarshal` call. However, ADR-0012 §1 specifies the reference as `network.*`, implying format flexibility. While the current network format is indeed JSON, this hardcoding creates a discrepancy. The code should either be made more flexible (e.g., based on file extension) or the ADR should be amended to explicitly state `network.json` is the required format for v1.

*   **Nit**: `engine/scenario/scenario.go:115:2`: The `Load` function is monolithic, intertwining path resolution, reading, decoding, validation, and preparing hashed parts. For the M11 scope, this is fine. However, for the upcoming overlay milestone, this structure will need refactoring. An overlay engine will need to: 1) load a base, 2) load a variant, 3) merge/patch the parts, and *then* 4) validate and hash the materialized result. Keeping this future requirement in mind during subsequent refactors will be important. The current `hashPart` struct is a good primitive for this, as it represents a piece of the final materialized scenario.
