## Findings

**Should-fix**

1. **`engine/cmd/metview/main.go:63` — `DeniedPending int` mismatches the writer's schema.** The file sink emits `denied_pending` as `float64` (engine/metricsjson.go:74, fed from per-lane `Pending float64` fractional-demand accumulators). Any run where the value is fractional (e.g. `3.7`) makes `json.Unmarshal` fail and metview `os.Exit(1)` on load — the tool refuses exactly the congested runs it exists to inspect. Change to `float64`. (Your four i280-pod variants presumably had integral or zero pending, so this wasn't hit.)

**Nit**

2. `engine/cmd/metview/main.go:30` — no `schema_version` check. The writer stamps version 1 (metricsjson.go:19); metview silently mis-renders any future version. One `if` at load time.
3. `engine/cmd/metview/main.go:353-368` — `rows` is built by ranging a map, then sorted with non-stable `sort.Slice` and cut to top-100. Ties order nondeterministically across requests, so the cutoff membership can flicker between refreshes. Add a `LaneID` tiebreak. (Viewer-only; no ADR-0005 exposure.)
4. `engine/cmd/metview/index.html:114,120,136` — run names, lane IDs, and trip types are injected into `innerHTML` unescaped. Local tool over your own files, so only a hygiene note — OSM-derived IDs are the one externally sourced string.
5. `engine/cmd/metview/main_test.go:462-486` — the anonymous interval struct type is repeated verbatim twice; a named type would halve the fixture. Cosmetic.

**Question**

6. `engine/engine.go:423-424` — the comment claims a chained crosser is "reconsidered there exactly as the sweep reconsidered it." Not exactly: the old sweep re-scanned `e.order`, so the crosser was reprocessed at its `e.order` position among lane `next`'s past-end vehicles; the new code appends it at the bucket's end. This is state-identical **only because** per-lane boundary handling is order-independent (no RNG, `pickSuccessor` is pure per-vehicle, Stats are commutative, despawn compaction runs after the loop) — which I verified holds today. If boundary handling ever becomes order-dependent (e.g. junction entry-capacity gating), intra-bucket order becomes load-bearing. Suggest one comment line naming that invariant as the thing future changes must preserve. The CRC-identical 7200-tick bench doesn't prove this branch — chained hops need a crosser overshooting a shorter, lower-index successor — but my reading says it's correct.

**Determinism verdict on the hot-path changes:** clean. The `past` map is indexed and deleted, never ranged (ADR-0005 safe); initial buckets preserve `e.order`; the `next.Index < i` re-entry condition exactly reproduces the old descending sweep's reachability, including multi-hop chains and the already-visited (index > i) skip. `totalLaneKm` cache: fixed slice order → bit-identical sum; zero-value sentinel only misfires on a zero-length network (recompute forever, harmless); single-goroutine constraint is documented and matches the two real callers. `Lane.Length` immutability, which the cache newly depends on, is asserted only in an **unstaged** comment (network.go:13-15 isn't in this patch) — fine, but note the shipping patch carries the dependency without it.

No blockers. Contract-wise nothing on NATS changed; metview consumes the existing ADR-0014 file schema read-only, no ADR needed.
