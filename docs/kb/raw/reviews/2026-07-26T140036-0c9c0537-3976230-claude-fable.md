Review of `docs/kb/decisions/ADR-0026-batched-intents.md` (docs-only diff; reviewed as the spec M1 will implement from). All cited file:line anchors check out (contract.go:923 publishObs, driver.go:350 publish, bus.go:239 onIntent, frame.go:140 ParseFrame, driver.go:22-25 emergent sharding), the 44 B fixed section is real (`intentFixedBytes = 44`, bus.go:40), the ~23.8k record cap and 1.7 MB/tick arithmetic are correct, and the apply-order description matches `applyIntents` (engine/intent.go:114-130). Subject unchanged + ADR filed satisfies the ADR-0006 §9 gate. Findings:

**Blockers** — none.

**Should-fix**

1. **ADR-0026:57 — "field-identical to the fixed section of intent v2 (vehicle id, seq, axes)": there is no seq in the v2 fixed section.** The 44 B layout is vehicle_id, flags, lane_delta, accel, speed_setpoint, signals, turn, route_len, reserved (engine/natsio/bus.go:27-31). Seq is assigned engine-side by the contract layer in arrival order (bus.go `ArrivedIntent` comment; engine/intent.go:65-71), never on the wire. This parenthetical is the wire-format definition the asyncapi schema and M1 codec will be written from — fix it before it propagates.

2. **ADR-0026:154-156 — same confusion in M2: "Per-vehicle seq counters … unchanged" and the "seq continuity across batches" test.** The driver has no seq counters (grep for `seq` in driver.go: zero hits). The property you actually need is that expansion preserves record order into the buffer so engine-assigned seqs stay monotonic per controller — state it that way or the M2 test is testing a fiction.

3. **ADR-0026:110-111 — "4 msgs/tick instead of 4,000" contradicts the ADR's own table.** 40k vehicles × 1 msg/vehicle/tick at the 10 Hz cadence (tick = 100 ms, BENCHMARKS.md §a) is 40,000 msgs/tick, per your own 400k msgs/s row. The correct number makes the case stronger, not weaker.

4. **ADR-0026:65-69 — record-level validity is undefined for the fields the reused layout drags in.** Records carry route_len and flag bit4 (route present) verbatim. Whole-batch validation is "exact-length + version" only, so a structurally valid batch can hold records with route_len≠0 or bit4 set — per-record `DecodeIntent` on a 44 B slice would reject them, which is exactly the partial application/partial drop the ADR forbids ("dropped whole … never partially applied"). Pin the rule now (simplest: any record with route_len≠0 or bit4 set ⇒ whole batch invalid); this is a contract edge the M1 tests and asyncapi schema must encode.

**Question**

5. **ADR-0026:53-54 — what does the engine do with the TSIB header `tick`?** v2 intents carry no tick; ingest is arrival-based and intents apply at drain tick. If the field is informational-only, say so (otherwise someone will "helpfully" validate against it and introduce a stale-batch rejection semantic v2 doesn't have); if it's meant to be checked, that's a semantic divergence from v2 the ADR must spell out.

**Nits**

6. ADR-0026:142-143 — "the gap was noted there": BENCHMARKS.md contains no such note (it measures 1/10/100 intents/tick pubacks and snapshot fan-out only). Drop the attribution or actually add the note in M0.
7. ADR-0026:24 — the 1.36M msgs/s figure is 8-subscriber *delivery* aggregate for 2.4 kB snapshot frames, not many-publisher 44 B intent ingest; fine as an order-of-magnitude anchor, but the shapes differ enough that M0's baseline is the real number.
8. ADR-0026:5 — "ADR-0006 §4 (live-plane message discipline)": §4 is titled the intent pipeline; the discipline language is §2/§6. Loose but findable.

Design-wise the load-bearing choice (wire codec only, expand at ingest, record plane untouched) is the right shape for ADR-0005/0023 replay determinism, and the explicit non-goals (no barrier, no shard assignment) match the repo's triage bar.
