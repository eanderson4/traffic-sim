# External review — staged diff (ADR-0016 TSSG chunking, ADR-0018 chunked GeoJSON, identity probe, themes)

## Blocker

**B1. Un-chunked signal tables throw on every broadcast — signals dead on all small/medium networks.**
`viz/src/tssg.ts:152` treats only `undefined` as "no sig_chunk header", but nats.ws `MsgHdrs.get()` returns `""` for an absent key, never `undefined` (verified in the pinned dep: `viz/node_modules/nats.ws/lib/nats-base-client/headers.js:186-194`, v1.30.3). Every TSSG publish carries headers (`tick`, `schema_version` — `engine/natsio/bus.go` PublishSignals always sets them), so `msg.headers` is defined and `headers?.get("sig_chunk")` yields `""` for a single-chunk table (no `sig_chunk` set when n==1). `parseSigChunkHeader("")` throws → `handleSigMessage` (`viz/src/main.ts:375`) catches, sets a HUD connection error, and never installs the table; the pull path (`viz/src/main.ts:354`) fails identically. Net effect: no lit signal heads and a spurious "bad sig_chunk header" error on every network whose table fits one chunk — i.e. every existing demo. The early-out in `viz/src/nats-client.ts` (`if (c) … else want = 1`) already treats `""` as absent, so the two call sites disagree on the same wire condition. Fix: `if (value === undefined || value === "") return null;` — an empty string cannot be a chunk coordinate, so this cannot misread a *malformed* header as "whole table". Add a test pinning `parseSigChunkHeader("") === null` (the current test suite pins the opposite at `viz/test/sigchunk.test.ts:4559`).

## Should-fix

**S1. `supervisor.start` holds `s.mu` through the 660 s identity wait — the whole control API freezes during big-city starts.**
`engine/cmd/demosrv/supervisor.go:141-142` takes `s.mu` for the full `waitReady` → `waitIdentity` span (`identityTimeout` 660 s; the diff's own numbers say la-lean world-build is ~400 s). `status()` (line 213) and `stop()` (line 187) block on the same mutex, so while a city demo starts, `/api/status` hangs (the menu polls every 3 s and piles up) and `/api/stop` cannot cancel a start — a wedged identity phase is only recoverable by killing demosrv. Before this change the lock hold was bounded at ~10 s, so the pattern was harmless; the 66× growth changes its character. Cancellable start (or probing outside the lock, re-checking `s.active` on completion) fixes it; at minimum, `status()` could be served from state captured outside the mutex.

**S2. Stale part requests trigger a full regeneration before the 404.**
`engine/cmd/demosrv/geojson.go` `part()` calls `c.path()` (which on a cache miss encodes the whole document — ~1 GB for la-lean, serialized under `c.mu`, blocking every other `/net/` request) *before* validating `wantSchema`/`wantHash`. A client holding a stale manifest can thus pay for (and make everyone wait on) a generation whose only purpose is to be answered with 404. Reorder: the schema check is a const compare and the hash check needs only `scenario.Load` — both can run before `path()`.

## Nits

- `engine/natsio/bus.go` `PublishSignals`: `noteFrameSize` runs even when the publish failed, so the 1 MiB watermark can log for a frame that never left. Cosmetic.
- `engine/natsio/probe.go`: `waitIdentity` dials a fresh WS NATS connection + JetStream context every ~1 s for up to 660 s of *normal* big-city startup — works, but a persistent probe connection would be far quieter in logs and broker accept churn.
- `viz/src/main.ts:375` uses the literal `"sig_chunk"` though `tssg.ts` exports `SIG_CHUNK_HEADER` for exactly this.
- `viz/src/main.ts` `activeThemeName = cfg.theme in THEMES ? …` uses `in` (prototype chain): `?theme=constructor` labels the toggle "CONSTRUCTOR" while `getTheme` (correctly `hasOwn`) renders navy. Cosmetic inconsistency.

## Questions

- **Broadcast cadence at city scale:** the ratified ADR-0016 keeps the 20-tick rebroadcast alongside the pull path, which for la-lean means ~7.3 MB every 2 s (~3.6 MB/s) to every live-plane subscriber, forever. The chunking makes drops cheap and the pull recovers them, so it's coherent — but was keeping the full-rate rebroadcast (vs. a slower cadence once chunked) an explicit trade-off? The INDEX's earlier "publish-once + request-reply *replacing* the rebroadcast" wording suggests the design moved; the ADR text records the final shape, so this is confirmation only.

## Checked and clean

- Determinism: no map iteration or wall-clock entered any sim/publish-order path; `SignalChunks` greedy pack is pure file-order; chunk cache is encode-once with tick patched by copy (`withSigTick` verified against the 24 B header layout, tick at offset 8); full-range `WriteGeoJSONRange` is pinned byte-identical to `WriteGeoJSON`.
- Contract: `sig_chunk` header, `ts.{run}.state.sig.req`, and the 4 MiB `MaxPayload` are all covered by ADR-0016 (ratified in this diff); the GeoJSON manifest/part shape by ADR-0018; `junction`/`row` properties ride the exporter `v2` cache-key bump. `.sig.req` cannot leak into existing consumers — all subscriptions are exact-subject and the recorder stream captures only `ts.{run}.log.>` (`engine/natsio/recorder.go:98`).
- The accumulator's generation logic (gap/regression/count-change reset, tick-is-not-identity, complete-swap-only) is sound and well-tested, including the paused-replay same-tick case.
- `handleNet` part-URL parsing correctly 404s non-part shapes (`d1.geojson.part-999` → schema cut fails); registry ids are token-only so the `.geojson.` cut is unambiguous.
- Manifest-last + temp/rename write ordering makes a killed generation regenerate rather than serve a half-set.
