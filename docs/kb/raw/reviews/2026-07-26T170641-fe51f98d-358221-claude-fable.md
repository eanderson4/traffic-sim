## Review — ADR-0026 M3 (batch-mode measurement + lag acceptance)

Shipped (non-test) surface is tiny and clean: `Bus.BufferedIntents` (bus.go:336-340, correctly mutex-guarded), `SubjectCtlAll` (server.go:786 — a subscription helper, no new published subject, no ADR needed), and the `tsibTickOff` constant refactor (tsib.go:806-811, byte-identical wire output). Verified against the repo: TSIB expansion lands records in `bus.buf` so the bench's `BufferedIntents < n` wait terminates in batched mode (bus.go:331-335); obs/ack headers are `tick`/`applied_tick` matching the tap (bus.go:49-51); ack-before-obs ordering claim matches run.go:184-185; the boundary test's one-intent-per-ego-per-obs assumption holds in driver.go:328-380, and route-update v2s go out on the same connection before the batch, so FIFO counting survives them.

**Blockers:** none.

**Should-fix:** none.

**Nits:**

1. `bus.go:336-338` — doc comment says "the boundary-controlled applied-lag test poll it," but `TestBatchAppliedLagBoundary` never calls `BufferedIntents`; only the bench does. Stale claim in a fresh comment.
2. `bench_intent_test.go:286-291` — the "applied-lag proxy" is a tautology: `hTick := e.Tick` at tick start and nothing steps the engine before the check, so `e.Tick - hTick` is structurally 0 regardless of what's in the TSIB header — it doesn't touch the header tick at all. The docs admit "0 BY CONSTRUCTION," but the two reported metrics (`lag_proxy_p50/p99_ticks`) are constants that pin nothing about the measurement path beyond "the harness is single-threaded." Consider dropping them rather than shipping metrics that can't move.
3. `driver_test.go:646-665` (warm-up quiesce) — the loop breaks on the first zero-fresh drain, but the driver's response to the final warm-up obs can still be un-arrived (or mid-stream with a delivery gap) at that instant; it then lands during measurement and trips the `attribute` desync Fatal at driver_test.go:679. Loud, not silent, and 2 ms sleeps make it rare — but it's the most likely flake seed in the file.

**Questions:**

1. `driver_test.go:768-773` — the fast-pace leg *requires* `v2Fast.splits > 0` and the acceptance comparison is exact-equality on percentiles from wall-paced runs. On a faster box (or after a driver-side speedup) 500 µs may stop straddling 400-vehicle v2 responses → hard failure with nothing wrong. The sibling test's comment (driver_test.go:462-463) already names the tolerance precedent for CI flakes; fine to ship under the no-hypothetical-hardening rule, but worth knowing this one is machine-speed-coupled in *both* directions (too fast kills the split precondition; and if v2 splits drop near zero while a TSIB batch occasionally misses a drain, `p99TSIB > p99V2` fails exactly).
2. `driver_test.go:1183-1186` — measured-loop drains are attributed but never `EnqueueIntent`'d, so "applies at u+1" is notional and vehicles run uncontrolled (default policy, not the HoldLast the live test uses) for the whole measured leg. Fine for drain-boundary timing, and a despawn would fail loudly via FIFO wedge — confirming that's the intent, since the comment at driver_test.go:667-668 says "exact by construction: a drain at pre-Step tick u applies at u+1" as if application happens.

Determinism: no engine-path changes; wall clock and sleeps confined to tests; the only new map (`touched`, driver_test.go:673) is membership-only, never iterated. Contract: no subject or payload changes (`SubjectCtlAll` is a wildcard for subscribers; TSIB bytes unchanged). BENCHMARKS.md numbers are internally consistent with the table and honestly caveated (same-session A/B/A/B vs the M0 baseline of record).

REVIEW-COMPLETE
