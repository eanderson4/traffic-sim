# External review — chicago-metro milestone (`651666a..d4673f8`)

## Blocker

**B1. Exit-destination draw reuses the vehicle main-stream RNG domain — destination choice is numerically correlated with policy draws** — `engine/natsio/driver/destinations.go:89`

`pickExit` derives its stream via `engine.DeriveStream(seed, vehicleID)`, which is `deriveStreamDomain("traffic-sim/engine/vehicle-stream", …)` (`engine/rng.go:22-24`). That is the *same domain and key* as (a) the kernel's per-vehicle main stream, which drives default policy for unclaimed vehicles — 28–84% of spawns at pace 0 per your own KB article — and (b) the driver's live policy stream (`driver.go:271`) consumed by `DecideLaneChange`. So the destination draw's uniform sequence is byte-identical to the prefix of the vehicle's lane-change/policy sequence.

Concrete failure scenario: with two eligible exits of roughly equal weight, every vehicle whose first policy draw is below ~0.5 is routed to the ID-sorted-first exit — the same coin decides both its route and its first MOBIL decision, fleet-wide, in every exit-routed run. Route choice and driving behavior are statistically coupled in exactly the way the engine's own `spawnAttrStream` comment (`engine/rng.go:26-33`) exists to prevent: "Distinct domain label keeps it independent of the main stream's schedule/policy draws."

The `destinations.go` header comment ("a FRESH per-vehicle stream … never the live policy stream") addresses draw-count independence but misses that a fresh stream *with the same derivation* replays the same values. It does not break replay or CRCs — recordings pin whatever happened — but it silently biases the milestone's core deliverable (credible circulation), and the fix is one line of domain hygiene (a destination-specific domain label, e.g. an exported salted variant of `deriveStreamDomain`). Fix it *now*, while the cost is zero: every scorecard tuning number and future demo recording binds to the current destination realization, and fixing later re-rolls every destination and invalidates tuning done in between. That is precisely the "before anything durable binds the result" window this review exists for.

## Should-fix

**S1. Liveness-detach semantics changed without updating `contracts/asyncapi.yaml` (or an ADR)** — `engine/natsio/contract.go:348` vs `contracts/asyncapi.yaml:202-208`

The contract doc states unconditionally: "an attached controller must produce an intent, claim, release, or heartbeat at least every DetachAfterTicks ticks (default 10) or it is detached." The milestone made this conditional — the sweep is skipped entirely when `PaceFloor == 0`. This is a semantics change to a documented contract guarantee (claims of a dead controller are now *never* released in a batch run), and per AGENTS.md rule 5 that requires an ADR and a doc update; the brief asked me to decide whether asyncapi.yaml should have been updated — yes. Aggravating detail: pace is an *unrecorded, client-invisible* run condition, so an external controller attaching to a run cannot know which liveness regime it is under. The engine-side reasoning (tick-space budgets assume pacing) is sound and well-documented in the KB, but the wire contract now lies. Minimum fix: amend the `ctlHeartbeat` description + a migration note; ideally record the decision (and the rejected alternative — a wall-clock silence budget for batch mode) in an ADR.

**S2. `zones.geojson` — the declared source of truth contradicts the milestone's own state: every zone is `import-pending`** — `scripts/chicago/zones.geojson:6-30`

The KB article declares three zones runnable with completed scenarios and scorecards (chi-loop, chi-kennedy, chi-north-lakefront), and the viz ships a runnable-vs-pending style split (`zrun` in `overlays.ts`, solid vs muted in `main.ts`). But the committed file marks all nine zones — including kennedy — `import-pending`, so with shipped data the `zrun=1` styling path is dead outside tests and the overlay renders every zone muted. Since `data/` is entirely uncommitted, there is also no committed record of how `scripts/chicago/zones.geojson` gets into demosrv's `-overlaydir` (`data/networks/overlays`) — the KB pipeline lists extract → netconvert → netimport → portals → mkdemand but never the overlay-population step. Update the statuses and document the copy step, or the file's "source of truth" claim is false.

**S3. `portals`: a lane that is both origin and exit is mislabeled** — `engine/cmd/portals/main.go:94-111`

`Origin` and `Exit` are independent flags (`engine/netfile.go:59-60`), and clip-boundary stub edges are routinely both (no predecessors *and* no successors). Such a lane gets `Kind: "exit"` (line 95-97) but is appended to the **origins** array (line 108-109): the inventory ships `{"kind":"exit"}` records inside `origins`, the exits list undercounts, and the summary counts are wrong. Today mkdemand ignores `kind` so demand still lands there (a ≥30 m isolated stub gets full class-rate injection into a lane vehicles exit one second later — inflating the "injected veh/h" total that the scorecard table reports as the zone's demand). Emit two portal records for dual-flag lanes, or at least make kind and array agree.

**S4. `pickExit` does O(network) work per claimed vehicle — on the zones this milestone targets, that feeds the documented claim-lag problem** — `engine/natsio/driver/destinations.go:36-63, 72`

Every first observation of a vehicle rebuilds and sorts the full exit-candidate list and runs a BFS over all lanes (56k+ for chi-north-lakefront, ~56 KB allocation each). At pace 0 the engine rips far ahead of wall time and spawn bursts hit the driver at hundreds per wall-second, so this sits directly on the path of the claim/routing lag your KB flags as a scorecard-fidelity problem ("finite-pace scorecard runs" is already a listed follow-up). Both computations are trivially cacheable: candidates once at `New` (the network is immutable), reachability memoized by `fromIdx` — vehicles are first observed on a small set of origin lanes, so the hit rate is near-total. This is not hypothetical hardening; it is a cheap fix to a measured problem on a roadmap item.

**S5. Overlays are global, not demo-scoped — every demo fetches and renders the Chicago overlays** — `viz/src/config.ts:23-28`, `engine/cmd/demosrv/main.go` (`-overlaydir`)

`zonesUrl`/`boundariesUrl`/`waterUrl` default to `/overlay/*.geojson` unconditionally, and demosrv serves one overlay directory for all registry entries. Once `data/networks/overlays` is populated, a DTLA or Berkeley demo fetches Lake Michigan and the Chicago zone partition and renders them — offscreen at network zoom, but visibly wrong the moment a user zooms out, plus a payload tax on every demo load. This bites today with the existing non-Chicago demos and structurally the moment a second metro gets overlays. The fix direction (per-demo overlay association in `demos.json`, or overlay files namespaced by network) needs a decision; right now the deferral is invisible — no KB/roadmap note records it.

## Nits

- **`scripts/chicago/boundaries.py:88`** — `sorted(b.feats)` sorts `(name, level, geom)` tuples; two features with equal name and admin_level (duplicate township names across counties are real in Illinois) fall through to comparing shapely geometries → `TypeError` crash. Sort with `key=lambda f: f[:2]`.
- **`scripts/chicago/water.py:128`** — `geom.intersection(clip)` can return a `GeometryCollection` (polygon-touch degeneracies); `mapping()` then has `"geometries"`, not `"coordinates"`, and line 128 raises `KeyError`. Latent for future zones.
- **`scripts/chicago/mkdemand.py:92,101`** — `skipped["scaled-out"]` is counted but never reported in the header or stderr summary; with `--total` scaling plus the 60 veh/h floor, the actual injected total can silently sit well under the requested `--total`. Your own review culture calls this "no silent caps."
- **`scripts/chicago/scorecard.py:42`** — the printed window `[max_end - ticks//4, max_end)` equals the true last interval only for a 1-hour run (default `PeriodTicks` = 900 s, `engine/metrics.go:88`); any other horizon mislabels the window (aggregation itself is fine — it keys on `end_tick == max_end`).
- **`engine/natsio/driver/driver.go:306-310`** — comment says the destination is "tried once either way," but the `Destination`-override path still retries every tick while `Route` fails (routed is only set on success there). Comment-vs-code drift.
- **`engine/natsio/driver/destinations.go:29` vs `engine/cmd/portals/main.go` `-fraglen`** — the driver's fragment cutoff is a hardcoded 30.0 while portals' is a flag; an operator changing `-fraglen` silently desynchronizes mkdemand's skip set from the driver's candidate pool.
- **`engine/cmd/serve/main.go` (attach path)** — `-attach-timeout` is reused as the driver's `MetaWait`, which bounds *each* of two sequential waits (registry meta, hello retry), while the barrier timer bounds the total; the driver can never actually use its nominal budget. Harmless today (in-process attach is fast; either path fails loud), just slightly confusing sizing.

## Questions

- **Q1.** In batch mode, is "no liveness at all" the intended long-term contract, or a stopgap until a wall-clock silence budget exists? Today a crashed *external* controller attached to a `-pace 0` run keeps its claims forever and its vehicles ride hold-last-then-default silently to the end. Fine for the embedded-clients-only use the KB describes — but nothing prevents an external attach to a batch run, and the run degrades with no signal. A one-line answer in the ADR from S1 would close this.

## Verdict

This is a strong milestone with unusually honest engineering writing. The attach-barrier design is the standout: parking *before* tick 0 with the contract plane served is the right generalization of the pause gate, the determinism note in `cmd/serve` is precise about exactly what is and is not pace-invariant, and `startgate_test.go` pins both the cross-pace directive identity and bit-identical replay — the two properties that actually matter. The batch-liveness root cause analysis is correct. The Python pipeline is appropriately napkin-grade for phase 1 and says so, and the KB article records its own defects better than most projects record their successes.

Two things keep this from being a clean pass. The RNG domain collision (B1) is small in code and large in principle — it violates the engine's own documented stream-separation discipline on the milestone's central new behavior, and it gets more expensive to fix with every tuning run and recording that binds to the current draws; fix it before the next scorecard round. And the liveness change (S1) is a real contract-semantics edit that shipped past AGENTS.md rule 5 — the KB article documents it, but the contract file now misdescribes engine behavior in a way clients cannot detect. Everything else is normal milestone residue, most of it already candidly recorded in the KB's known-defects list.
