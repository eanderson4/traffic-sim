Review of the staged deploy diff (10 new files, deploy-only; no engine/contract code in the patch — but the manifests bind directly to demosrv/serve behavior, which I checked in the tree).

## Blockers

**B1 — Public exposure of the unauthenticated, publish-capable engine ws plane, which ADR-0020 explicitly gates go-live on.**
`deploy/k8s/ingress.yaml:34-43` + `deploy/README.md:16-18` wire `ws.phantomjam.com` (public DNS, cert, LB) straight to the embedded NATS websocket listener — `engine/cmd/serve/main.go:218` runs it `NoTLS`, no users/permissions, so any internet client can publish `ts.{run}.ctl.intent.>` and hit the JetStream APIs. ADR-0020:102-114 (sol review, same day): *"Before the public ws endpoint is exposed, the broker needs an auth/permissions design… Treat this as gating the go-live."* This diff **is** the go-live. Nothing in the tree (including the unstaged engine work) adds broker auth, and `deploy/README.md` doesn't even carry the warning. Either broker auth lands first, or the manifests/README must be explicit that `kubectl apply` + DNS is forbidden until it does — as staged this commits the repo to violating its own ADR.

**B2 — The admin token leaks into every engine child's environment and onto argv, defeating the control the code just built.**
`deploy/k8s/deployment.yaml:42-46` injects the secret as env `ADMIN_TOKEN`; `deploy/docker-entrypoint.sh:13` passes it as `-admintoken "$ADMIN_TOKEN"` and leaves `ADMIN_TOKEN` in the environment. But `stripEnv` strips only `DEMOSRV_ADMIN_TOKEN` (`engine/cmd/demosrv/deploy.go:31`, `main.go:246`), so every spawned serve/replay child — the process serving the public unauthenticated ws plane — inherits the token in `/proc/<pid>/environ`; it's also world-readable-in-container on demosrv's cmdline. `deploy.go:28-31` and ADR-0020:55-58 state the env intake exists *precisely* to avoid argv. Fix is one rename: call the env var `DEMOSRV_ADMIN_TOKEN` in deployment.yaml, drop `-admintoken` from the entrypoint (the documented fallback + fail-closed empty-check already cover it; keep the entrypoint's presence check if you want the clearer boot error).

**B3 — The ws BackendConfig health-checks `/healthz` on 8443, which nothing serves; the ws backend will be permanently unhealthy.**
`deploy/k8s/backendconfig.yaml:22-24`. Port 8443 is the embedded NATS websocket listener — it answers non-upgrade GETs with an error, serves no HTTP paths, and between run swaps (and for the whole demosrv-idle case ADR-0020:77-89 describes) nothing listens at all. `grep -ri healthz engine/` returns zero hits; `deploy/README.md:27` admits the image "requires … the engine /healthz endpoint" that doesn't exist. As staged, GCE marks the ws NEG unhealthy and every `wss://ws.phantomjam.com` dial 502s — the deployment cannot work. Either ship the endpoint (or a sidecar/TCP-check strategy) with this change, or don't stage manifests that reference it.

## Should-fix

**S1 — initContainer copy command is unverified gcloud syntax and skips `mkdir` for its destination.** `deploy/k8s/deployment.yaml:32` uses `gs://…/scenarios/.` — the `/.` suffix is not a documented `gcloud storage` wildcard (the documented contents-copy form is `…/scenarios/*`), and `/data/scenarios/` doesn't exist on the fresh emptyDir (the netcache line at :33-34 does `mkdir -p`; this one doesn't). If the copy fails or nests one level deep, demosrv fatals at registry load (`registry.go` `checkDir`) and the pod crash-loops. With `set -e` semantics (`-ec`) verify this exact line against the real bucket before it's the thing between you and a boot.

**S2 — The runbook's one operational command is wrong on both host and path.** `deploy/README.md:48`: `https://phantomjam.com/api/start/<demo-id>` — the apex is in neither the ManagedCertificate nor the Ingress rules (only `app.`/`ws.`), and the route is `POST /api/demo/{id}/start` (`main.go:406`). Should be `https://app.phantomjam.com/api/demo/<id>/start`.

**S3 — Public-facing blurb numbers contradict the code's own figures.** `deploy/demos.public.json:6` says LA is "234k lanes", `:21` says SF "33k lanes"; `main.go:287-289` (same tree) says la-lean is 1.38M lanes and sf-lean 303k. One generation of the -lean imports is being misdescribed — confirm which is current before the copy goes public.
