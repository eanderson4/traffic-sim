Review of the staged ADR-0026 M1 diff (TSIB codec, header demux, expand-at-ingest). Checked against ADR-0026, the v2 codec in bus.go, the contract drain path, and the embedded test server. No blockers found; the implementation matches the ADR's wire format, demux rules, structural-validity list, and named backstops closely, and the M1 test list from the ADR is fully covered.

**Should-fix**

1. `engine/natsio/tsib.go:98` — A NaN/Inf TSIB record drops with **no counter**. In v2 the same bad payload increments `b.dropped` (`bus.go:314`); in a batch the record just silently vanishes (`intentRecords` is documented "post NaN-drop", `bus.go:213`, so the gap is by design but invisible to an operator). ADR-0026 sells the counters as "the observability substitute" and claims NaN drops happen "in parity with a bad v2 message dropping alone" — the drop is in parity, the counting isn't. Have `DecodeTSIB` return a dropped-record count (or count in `onIntent`) and add it to a counter. Cheap now, and it's the only way to distinguish "controller sent fewer records" from "records rejected".

2. `engine/natsio/tsib.go:51` — `EncodeTSIB` with more than `TSIBMaxRecords` non-route intents silently emits a batch that every compliant decoder (including its own, `tsib.go:82`) must drop whole. Splitting is M2 driver work, but the exported encoder producing invalid-by-construction wire bytes with no error is a trap for any M1-era caller. Minimum: state the `len ≤ TSIBMaxRecords` precondition in the doc comment; better: guard it. Defer-to-M2 is a defensible triage if recorded.

**Nit**

3. `engine/natsio/tsib.go:57` — `EncodeTSIB` silently skips `RouteSet` intents with no signal to the caller (no skipped count returned). Correct per the ADR — the M2 driver diverts them to standalone v2 — but until M2 lands, a caller that forgets the diversion loses route intents without a trace. Fine to leave; noting it.

4. `engine/natsio/bus.go:296–330` — The v2 decode-and-append block appears verbatim twice (headerless fast path and `case ""`). The fast-path duplication is justified by the comment; the two copies could still share a tiny method without touching the hot path. Cosmetic.

**Question**

5. `engine/natsio/tsib.go:12` — Header `flags u16` and `reserved u32` are reserved-zero on encode but **not validated on decode**. That matches the ADR's structural-validity list exactly (length, version, cap, route rule), but it means those bits can only ever gain ignorable semantics — any must-understand use requires a version bump. If that's the intent (version is the mechanism), fine; worth a word in the M4 asyncapi note so the choice is recorded.

Verified non-issues, for the record: the `count > TSIBMaxRecords` check short-circuits before the length multiply, so no 32-bit overflow; headerless multi-record TSIB always fails v2 structural validation (implied `route_len` ≥ 68 > `intentMaxRoute` 48), and the single-record 68-byte pathological case is claim-filter-backstopped and pinned by test; `Header.Set`/`Get` canonicalize consistently (incl. cross-client via `ReadMIMEHeader`), so the `intent_encoding` key round-trips; expansion order is deterministic (single delivery goroutine, append under lock, record order); 880,024 B boundary payload fits both the default 1 MiB server payload cap and the 4 MiB embedded-broker config; drop logging is capped at 3 per run so the hot path stays quiet; the `b *testing.B` → `tb testing.TB` bench refactor is behavior-neutral. The asyncapi.yaml contract update is deliberately deferred to M4 per the ADR, so its absence here is not a contract violation.
