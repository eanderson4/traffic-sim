## Findings

**Should-fix**

1. **driver_test.go:721-728 (patch) — delayed-probe assertion races the driver's response.** The extra drain runs immediately after `AfterStep` publishes obs T and asserts `fresh2 == 0`. Nothing synchronizes "the response has not arrived yet": if the test goroutine is preempted between `AfterStep` and `DrainIntents` for longer than the obs→driver→intent round trip (~100 µs on loopback), the fresh response lands in the buffer and the test fails — in v2 mode even a *partial* arrival fails it. In practice the in-process drain almost always wins the race, but this is a wall-clock-dependent assertion in the default test path on a shared box; it's the same class of flake the sibling test explicitly budgets a +1 tolerance for, yet here it's a hard `Fatalf`. Cheap fix if you want one: drop only the `fresh2 != 0` Fatal to a `t.Logf`/skip-sample (the lag-2 assertion on the next iteration still catches a response that *made* the boundary, because lag would be 1). Per the repo's own triage bar this can also be a defer-with-note.

2. **driver_test.go:611 (patch, `for d.FleetSize() < vehicles`) — claim warm-up loop has no deadline.** Every other wait in this test (`pumpDeadline`, `waitBuffer`) is bounded; a stalled claim path hangs until the package `go test` timeout with no diagnostic. One `time.Now().After(deadline)` check matching the others would fail loudly instead.

**Nit**

3. **driver_test.go:744-748 (patch) — the "exact, no tolerance" percentile comparison is vacuous.** Every sample is already pinned per-tick to exactly 1 (immediate) or 2 (delayed) by earlier `Fatalf`s, and both legs run the same schedule, so `p50TSIB > p50V2 || p99TSIB > p99V2` can never fire — a leg that shifted would have died at the per-sample assert. Harmless as documentation, but the comment sells it as the regression check when the per-sample asserts are.

4. **bench_intent_test.go:286-291 (patch) — `lagSamples` is all-zeros by construction** (Fatalf fires on any nonzero), so the sort/percentile block at 357-362 always reports 0/0. Self-acknowledged in BENCHMARKS.md ("BY CONSTRUCTION"); fine as a measurement-path pin, but the dead percentile machinery could be two `ReportMetric(0, …)` lines.

5. **driver_test.go:900 (`tap.lastSrc = int64(tap.lastObs)`) — v2 pairing can use a stale/zero `lastObs`** if the driver responds to an obs published before the tap's subscription went active (tap attaches after `driver.New` returns). Worst case is a handful of early inflated samples; percentiles over ~400 samples and the sample-count floor absorb it. Documented ±1 covers the steady state, not this startup edge — not worth code, worth knowing.

**Question**

6. **driver_test.go:869-872 — deliberate literal re-pinning of `intent_encoding`/`tsib`/offset 8** in the external-consumer test package: confirmed intentional per the comment, and it correctly mirrors bus.go:51-54 and tsib.go's `tsibTickOff`. No action; flagging only so a future TSIB v2 header change knows this test pins v1 layout in two places.

**Contract/determinism check — clean.** No NATS subject or payload changes: `SubjectCtlAll` (server.go, patch line 762) is a subscription convenience over the existing `ts.{run}.ctl.>` tree, not a new published subject; `Bus.BufferedIntents` is a read-only Go API; tsib.go is a pure const refactor with the round-trip test updated to match.
