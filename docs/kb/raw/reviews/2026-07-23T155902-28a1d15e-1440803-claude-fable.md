## Findings

**should-fix — durable `-store` + reused run id silently appends a second run into the recording it exists to preserve.**
`jetStreamStoreDir` (main.go:344-357 new) keeps the store, but `NewRecorder` adopts an existing stream (`js.AddStream` is create-or-adopt with identical config — engine/natsio/recorder.go:74-92). Rerunning `serve -store dir` with the same run id — and the default is `-run demo` (main.go:47) — appends a fresh tick-0 keyframe and a second run's whole log after the first run's messages in `StreamName(run)`. Replay of the "durable, for replay" recording then reads interleaved history from two different runs (possibly different seeds/scenarios). The new doc comment warns only about two *concurrent* brokers, not sequential reuse, which is the likelier operator mistake. Cheap guard: when `-store` is set, `StreamInfo` before running and fail (or at least loudly warn) if the run's stream already exists non-empty.

**should-fix — scenario-set `dt` never reaches the viz; speeds silently scale by the ratio.**
Scenarios can set `params.dt` (engine/scenario/scenario.go:331-332), and serve knows `spec.Params.Dt` — it feeds `paceFloor` (main.go:149). But the printed viz hint (main.go:305-306) is `?run=…&ws=…` with no `&dt=`, and viz `loadConfig` defaults to 0.1 (viz/src/config.ts:255). A `dt: 0.05` scenario shows every vehicle at 2× speed and free-flows the congestion overlay — exactly the bug class this diff fixes for pace, reintroduced through the other variable in the same product. One-line fix: append `&dt=%g` to the hint printf (already have `spec.Params.Dt` in hand). Not a NATS contract change, so no ADR needed — but note ADR-0006's TSSF v1 carries no dt, so URL/hint is currently the only channel.

**question — `-pace 0` help text sells "fast recording", but the default `-driver` replica can't keep up unpaced.**
natsio's own doc warns that an unpaced loop spins at ~10⁴ ticks/s and "even in-process controllers lag dozens of ticks" (engine/natsio/contract.go:58-59). With `-driver true` (default) plus `-pace 0`, the recorded run is mostly hold-last/uncontrolled behavior, not what a paced run would record. Replay stays deterministic (log is authoritative), so this isn't a correctness bug — but is a batch recording of a driver-starved run the artifact you want? If intended, a one-clause caveat in the `-pace` help string would save the next user the surprise.

**nit — `paceFloor` rejects NaN and negatives but accepts `+Inf`** (main.go:334-346): `dt/Inf = 0` → silently unpaced. Since you bothered to validate NaN, `math.IsInf(pace, 1)` deserves the same error (or the doc comment should say Inf ⇒ batch mode). Huge-but-finite pace rounding the floor to 0 is fine — the "unpaced (batch mode)" startup line surfaces it.

Clean elsewhere: the sim-time speed derivation is correct (tick-delta × dt is decimation-proof; `simSec <= 0` guard covers duplicate/held frames, matching the old `dtSec` fallback); default `-pace 1` reproduces the pre-flag floor exactly, and the tests pin that; pacing is wrapper-only per ADR-0005 §4 — no determinism-relevant state touched; no NATS subject/payload changes, so no ADR trigger; `?dt=` URL validation (finite, > 0) is sound; tests cover the flag plumbing on both sides.

No blockers.
