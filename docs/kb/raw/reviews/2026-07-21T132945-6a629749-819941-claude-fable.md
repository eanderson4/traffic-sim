## Blocker

**B1. Ring networks silently corrupt VMT/time-loss on every wrap.** `metrics.go:294-296` — the `prev.lane == lane` branch computes `d = v.S - prev.s` with no wrap handling. The ring net is a single lane that is its own successor (`network.go` — `r.Successors = []*Lane{r}`), and `boundaries()` wraps via `S -= lane.Length` with `Lane` unchanged as a pointer. So a wrap tick hits the same-lane branch with `d ≈ movement − Length` (e.g. −228 m on the Sugiyama ring): VMT and the lane's `sumDist` go negative by ~one circumference, and `tl = dt − d/v0eff` injects ~+27 s of spurious time-loss per vehicle per lap. The `isSuccessorCrossing` branch that would split correctly is unreachable because the pointer-equality case wins first. Ring is a first-class net kind (`DefaultSpec("ring", …)` exists) and `NewKernel` accepts it without complaint — numbers are silently wrong, the failure mode ADR-0014's strict-fence philosophy exists to prevent. Minimal M13-honest fix: reject self-successor lanes loudly in `NewKernel`, or handle `v.S < prev.s` on self-successor lanes as a crossing.

## Should-fix

**S1. Pre-placed vehicles book their initial position as driven distance.** `metrics.go:283-285` — the first-observation branch assumes "spawned at S = 0 in phase 1 of this tick" and counts `dist = v.S`. True for spawner/director injections (both set `S = 0`), false for the ring `InitialVehicles` population and `AddInitialVehicle` (placed mid-lane before the first Step). A 22-vehicle Sugiyama ring gets ~2.4 km of phantom VMT at tick 1. Clean fix: seed `k.last` from `e.Vehicles()` inside `NewKernel` (it already receives `e`), which also documents "attach before the first Step".

**S2. Interval grid is shifted one tick from its stamped bounds.** `metrics.go:616-644` — observations exist only for ticks 1…N (`Observe` after `Step`), but with the default `BeginTick = 0` the first interval `[0, P)` accumulates only P−1 observations while `closeInterval` divides by `P·dt`: Q/K/Occupancy biased low by 1/P in the first interval (0.01% at P=9000, 10% at P=10 — window-dependent, which is worse for comparisons). Symmetric artifact: a horizon landing exactly on the period grid (N = kP) emits a trailing 1-tick `Partial` per lane, whose data comparison tooling then drops. Since obs tick T covers sim time (T−1)·dt…T·dt, mapping tick T to interval `(T−1−Begin)/P` (i.e. intervals hold ticks `(B, B+P]`) makes bounds, durations, and observation counts all agree. ADR-0014 §3's "intervals align to tick 0" pin is about `begin_s` grid alignment, not this off-by-one, but whichever convention ships here binds recordings — decide before the sinks land.

**S3. Director directives accrue "denied" wait before they are due.** `metrics.go:422-424` — every `dirQueue` entry accrues `dt`, with no `EarliestTick` check, while the spawner path two lines up correctly guards on `st.tick <= tick`. A directive with `EarliestTick` in the future is scheduled demand, not denied demand; it inflates `DeniedWaitS` and contradicts both the kernel's own comment ("whose scheduled tick has passed") and ADR-0014 §3's request-tick semantics. Same gap in `Finalize` (`metrics.go:469-471`): future-eligible directives count as `DeniedPending`. Fix: `if d.EarliestTick <= tick` in both places.

**S4. The despawn tick's travel is entirely unaccounted.** `metrics.go:393-407` — a vehicle observed at `prev.s` that exits during the next tick is only noticed as gone: its final segment (`prev.s` → lane end, up to `v0·dt` ≈ 3.3 m) and its final `dt` of presence reach neither VMT/VHT, the exit lane's Edie sums, nor the trip's `DistanceM` — a systematic per-completed-trip undercount and a downward q bias at exit boundaries. ADR-0014 §3 doesn't pin exit accounting, so this may be an acceptable v1 approximation — but the boundary-split machinery it bypasses is pinned, so either close the gap (the exit segment is a `dOld`-only crossing with no new lane) or document the exclusion where the crossing approximations are documented.

## Nit

- `metrics.go:16` — header claims accumulation is "in e.Vehicles() order (ID order)"; `Vehicles()` returns `e.order`, which `engine.go:151-154` explicitly documents as spawn/append order, *not* ID order. Deterministic either way (no bug), but the comment repeats a stale claim from `engine.go:174`.
- `metrics.go:231-265` — `NewKernel` doesn't reject `EndTick > 0 && EndTick <= BeginTick`; such a set silently never accumulates and emits nothing, against the fail-loud fence the constructor advertises.
- `metrics.go:327-335` — in the crossing branch, when the summed tick loss passes the clamp, a negative per-side share (vehicle above `v0eff` on one lane) is still added to that lane's `sumTimeLoss`; the non-crossing branches never add negatives. A lane's interval `TimeLossS` can dip below the sum of its per-tick clamped contributions. Documented-ish; fine to leave, worth a comment.
- `metrics.go:630-639` — a set whose `EndTick` falls mid-run holds its final remainder open until `Finalize` instead of emitting when the window closes; harmless for the file sink, adds full-run latency for the future live NATS consumer.
