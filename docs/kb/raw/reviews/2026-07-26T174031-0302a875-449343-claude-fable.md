## Should-fix

1. **`driver_test.go:1226` (patch L795) — measurement loop never enqueues drained intents.** Warm-up and quiescence phases call `e.EnqueueIntent(k)`; the measured loop calls `attribute(…, contract.DrainIntents(e))` and drops the result. So "COMPLETE-application" is by-construction (drain at u ⇒ would apply at u+1), never observed, and the driver's intents have zero effect on vehicle dynamics during measurement. This is arguably the *right* design — it keeps both legs' engine trajectories bit-identical so v2's straddle can't feed back into dynamics/obs and confound the comparison — but nothing in the extensive test doc says it's deliberate, and a future reader will "fix" it by enqueuing. One comment line either way.

2. **`bench_intent_test.go:286-291` — the lag proxy is a tautology, and the comment overclaims.** `hTick := e.Tick` at the top of `runTick`; nothing mutates `e.Tick` before the check (`e.Step()` is after), so `lag := int64(e.Tick) - int64(hTick)` compares a variable to itself. The `Fatalf` is dead code and `lag_proxy_p50/p99` are 0 by identity — it does not "pin the measurement path (demux/expansion adds no engine-side tick)" as the file header (line 36-40) claims, because nothing that traversed the wire is ever read. BENCHMARKS.md is honest ("0 BY CONSTRUCTION") but the bench comment isn't. Either decode the header tick back out of a drained record (that would actually pin demux), or drop the metric and the claim.

## Questions

6. **`driver_test.go:1338` — `v2Fast.splits == 0` is a hard Fatal in the *opposite* direction of the usual flake:** the 1.5 ms pace is tuned to this box; a faster machine where 400 v2 messages always land within one boundary would fail the "case exercised" pin. You've measured 18–23/300 with margin, and the repo rule defers hypothetical hardening — flagging so the tuned constant is a known knob, not asking for a guard now.
