## Review — replay Player (VCR driver) + shared log index

**No blockers found.** The concurrency design (single Run goroutine owns the engine; pause/seek serialized over `ctrlCh`; resume/speed as mutex-guarded flags) is sound, the determinism discipline holds (intents/verbs re-enqueued in stream order from per-tick slices — no map iteration in the sim path; wall clock confined to pacing/publication per ADR-0005 §4), and `indexLogMsgs` is a faithful extraction of the old `ReplayFromStream` loop (same decode paths and errors, keyframe ticks added). The test's end-to-end CRC equality against the live run is the right anchor.

### Should-fix

1. **Contract change without an ADR note** — `engine/natsio/server.go:187-199`, `run.go:64-68`, `recorder.go:76`. This diff (a) narrows the public run-id discipline: `RunLive`/`NewRecorder` now refuse previously-valid ids ending in `-replay`, and (b) introduces a new published plane, `ts.{run}-replay.state.snap/sig`, that viz clients are expected to consume. Per AGENTS.md rule 5 and ADR-0006 (which has no mention of the replay namespace — I checked), the reservation and the replay-plane semantics need an ADR-0006 addendum + migration note. Can ship as the companion docs commit, but it should land with this milestone, not later.

2. **HTTP control plane vs ADR-0002** — `engine/cmd/replay/main.go:47`, `player.go` `Handler()`. ADR-0002: "All inter-service communication flows over NATS. No direct service-to-service RPC." The demo UI driving `/pause /resume /speed /seek` over HTTP is exactly that. It may be a reasonable carve-out (ops tooling for a replay tool, not sim-state communication — the engine-authority invariant is untouched since the player publishes only), but that's a decision of consequence: record the departure in the same ADR addendum, or route controls over NATS subjects. Raising rather than silently diverging, per rule 1.

### Nits

3. `paceSleep` (player.go:529) keeps draining the original deadline after servicing a pause, so at very slow speeds (0.01 → 10 s floor) the first paused republication — and the frame at the paused tick, which the decimation stride may never have published — can lag by the remaining floor. The "no further tick" guarantee holds; only frame latency. Trivial fix if wanted: bail out of `paceSleep` once paused.
4. `/resume`'s done-check (player.go:689-696) is check-then-act against the Run goroutine's done/paused transition (end-of-record CAS, and `seek`'s `done.Store(false)` → conditional re-set). A racing `/resume` can leave `/status` showing `done=true, paused=false`; the hold itself is safe (gated on `Tick >= endTick`), so this is cosmetic only.
5. The tick-floor range check (`v < 1` branch, player.go:381 and the `/speed` handler:710) rejects very high speeds (> dt·1e9 ≈ 1e8×) where `tickFloor` would truncate to 0 and the existing `floor > 0` guard already makes pacing a no-op — over-restrictive, and the check is duplicated verbatim in two places; worth a shared helper if touched again.
6. `decimation`'s doc claim "~10 Hz wall at any pace" (player.go:766-769, echoed in the `-speed` flag help) holds only for dt = 100 ms; generally it's ≈1/dt Hz. Doc-only.
7. main.go:129 prettifies the ws URL for `""`/`"0.0.0.0"` but not `"::"` — prints an unusable `ws://[::]:port`. Print-only.

### Questions

8. Is single-broker store exclusivity worth a runtime guard (e.g. a lock file in the store dir) rather than convention + demosrv kill-before-spawn? Two brokers on one JetStream store dir corrupts silently. "Too early to need this" is a fair triage outcome — flagging because the failure mode is data loss on the durable record.
