Review complete. I read the full staged patch, verified it against the working tree (engine tick-stamping, all `log.intent` readers, nats.go v1.52.0 `Fetch`+`PullMaxBytes` semantics), ran the full `natsio` test suite (pass, 59s) and `go vet` (clean).

## Findings

**Blockers:** none.

**Should-fix:** none. The one candidate I chased hardest — the recorder's new mixed-tick abort (`recorder.go:421-426`) false-positiving — is sound: `Step()` increments `e.Tick` first (`engine/engine.go:337`), `applyIntents` stamps every record with that same tick (`engine/intent.go:140`), and `LogTick` reads `e.Tick` after Step, so writer-side ticks always agree.

**Nits:**
- `engine/natsio/recorder.go:383` — `loggedIntentMax` budgets 256 B for the controller name, but `appendLoggedIntent` (`recorder.go:364`) never enforces it; the real bound is only the transport's subject-token limit (~4 KB control line). An oversized id would push a TSLB message past `IntentBatchMax` — harmless under NATS' 1 MiB max payload, but the comment claims a guarantee the code doesn't hold. A `len(ctl)` cap or a comment correction would close the gap.
- `engine/natsio/tslb.go:1041-1053` (`DecodeTSLB`) — `count := int(uint32)` can go negative on a 32-bit build; the `count > len(rest)/loggedIntentMin` guard passes it and `make([]engine.TickedIntent, 0, count)` panics with a negative cap — a crash where the decoder promises a loud error. Irrelevant on amd64; one `count < 0` check if 32-bit ever matters.
- `engine/natsio/recorder.go:167-175` — StreamInfo-then-UpdateStream in the adopt path is a TOCTOU window (a message landing between check and update gets its stream reconfigured). Theoretical under the sole-writer invariant; noting for the record only.
- `DecodeTSLB` accepts a `count=0` batch the writer never emits (`logIntentBatch` returns early on empty). Lenient but harmless; the contract text says "a tick with no applied intents emits no batch", so a strict reader could refuse it.

**Questions:**
- `engine/natsio/logcursor.go:331` — the `cursorBatchBytes` cap is never actually hit by any test (test recordings are far under 16 MiB per fetch). I verified from nats.go v1.52.0 source that a server 409 max-bytes termination after partial delivery returns the collected messages with a nil error, and `nextMsg` then advances `curSeq` off the last delivered message, so the logic is right — but the first code to exercise it will be a real chi-scale replay. Deliberate? (A one-off manual replay of a batched recording would retire it; the reader is fixable post-hoc either way, since nothing durable binds to it.)

**Contract/ADR discipline:** exemplary — new subject + payload get ADR-0035, an ADR-0006 addendum, an ADR-0026 supersession note, an AsyncAPI minor bump (2.5.0→2.6.0) with migration text matching the code (header layout, 768 KiB default, split semantics all cross-check). `log.intents` vs `log.intent` are distinct NATS tokens, so no filter half-matches; `SubjectLogAll` covers both. Determinism: no map iteration, no wall clock, no RNG in any new encode/decode path; split points are deterministic from config. The shared-codec migration test (recorder → real JetStream → production reader, both formats, splits forced) is exactly the right shape for a record-plane change.
