## Findings

**Blockers:** none.

The race machinery is the risky part of this change and it holds up under adversarial interleaving: `shutdownFinal`'s closed→pending→epoch store order vs `startGuarded`'s epoch-snapshot→pending-check→second-closed-check order leaves no window where a start both dodges the latch and keeps a matching epoch (if the start snapshots the post-bump epoch, `stopPending` is still ≥1 because the decrement needs the mu the start holds). The reaper closes `a.done` *before* taking mu, so `stopLocked` waiting on `done` under mu can't deadlock; the `s.active == a` guard makes the reaper safe against swaps; the corpse-clear in `startIfIdle` composes with both. `errStartAborted` survives the `%w` wrap in `start`, so autostart's `errors.Is` triage is sound. Contract-wise: no NATS subject/payload changes; the HTTP-surface change (401s on the mutating POSTs) is covered by ADR-0020, which also correctly flags the real go-live hazard — the unauthenticated publish-capable ws plane — as a deployment precondition rather than pretending this commit addresses it.

**should-fix**

1. `engine/cmd/demosrv/supervisor.go:249-254` (patch: startGuarded's `stopPending` check) — the queued-stop refusal applies to *operator* `start()` too, not just autostart, and `handleStart` (main.go:488) maps it to a bare 502 `"start aborted (stop requested)"`. A menu user who clicks stop-then-start fast enough to land in the pre-mu window of the stop gets a confusing 502 for a start they did intend; previously the start would queue and win. The window is milliseconds when idle but up to `killGrace`+readiness-abort when a run is draining. If intended (comments suggest it is), a note in ADR-0020 or a 409 with a "stop in progress, retry" body would make it deliberate rather than incidental; at minimum record it as a known semantic change to `/api/demo/{id}/start`.

**question**

2. `engine/cmd/demosrv/supervisor.go` `waitReady` (patch line ~1645) — when tests inject `s.ready`, the epoch/done abort checks are bypassed entirely, so no test can exercise the real probe-abort path end-to-end (the epoch tests all go through the guard checks instead). Is there coverage anywhere that a stop epoch bump actually aborts a live `waitPort`/`waitIdentity` loop? If not, that's the one load-bearing path validated only by inspection.

**nit**

3. `engine/cmd/demosrv/main.go:1266` (patch) — `ReadHeaderTimeout` alone: a slow-loris *body* on the ctl-forward POSTs (`forwardCtl` reads the request body) still holds connections indefinitely; `IdleTimeout` is also unset. Deliberately-thin per the triage bar ("infra owns abuse"), and `WriteTimeout` would break the huge `/net/` responses, so plausibly "too early" — noting for the record only.
4. `engine/cmd/demosrv/main.go` (patch ~1144, "flag validation FIRST") — the `-nobuild` stat-check actually runs *after* registry load and `MkdirAll`, mildly contradicting the fail-in-milliseconds comment. Cosmetic; registry load is cheap.

Determinism: nothing engine-core is touched; no map iteration in sampled paths, no RNG, and the wall-clock use (backoff, timeouts) is orchestration-side where it belongs. `stripEnv` preserves environ order. The one unconditional local-behavior delta (10 s `ReadHeaderTimeout`) is documented in the ADR.
