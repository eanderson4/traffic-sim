## Findings

**BLOCKER**

1. `deploy/k8s/cronjob.yaml:70` — the `resources:` block is indented as a sibling of `containers:` (pod-spec level), not inside the `kubectl` container. Outcome depends on cluster version: on <1.32 the apply in README step 3 fails strict server-side validation (`unknown field spec.jobTemplate.spec.template.spec.resources`), breaking the documented deploy pipe; on ≥1.32 the field parses as pod-level resources — either silently dropped (feature gate off) or applied with unintended semantics. **SHOULD-FIX**

2. `deploy/k8s/ingress.yaml:22` — `networking.gke.io/v1beta1.FrontendConfig: https-redirect` references a FrontendConfig that is defined nowhere in the diff or repo. FrontendConfig is namespaced and `traffic-sim` is created fresh here, so the object cannot pre-exist; the ingress will sync with errors and the HTTP→HTTPS redirect will silently not happen (plain-HTTP `app.phantomjam.com` serves the app, including the token in any operator's pasted curl). Add a `FrontendConfig` with `redirectToHttps: {enabled: true}` next to the ManagedCertificate, or drop the annotation. Go-live-gated file, but the manifest is incomplete as staged.

**NIT**

3. `deploy/k8s/deployment.yaml:449-451` (initContainer script) — `gcloud storage cp` is overwrite-only; on an init-retry within one pod's life, objects deleted from the bucket linger on the emptyDir. `gcloud storage rsync -r` is the idempotent form. Bounded by pod lifetime; fine to defer.
4. `deploy/README.md:130` — step 4 pipes `ingress.yaml` through the `:TAG` sed although it contains no `:TAG`. Harmless, but implies a coupling that doesn't exist; plain `kubectl apply -f` would document intent better.
