**Should-fix**

1. `engine/natsio/driver_test.go:838-847` — the fast-pace leg's `v2Fast.splits == 0` → `t.Fatal` hard-codes a machine-speed assumption into the default test path. The 1.5 ms pace was tuned so boundaries fall mid-response *on this box*; on a faster machine the 400-message v2 stream may never straddle a drain (splits = 0 → spurious failure), and on a slower/loaded box overruns compound. The structural half of the pin (`tsibFast.splits != 0` → fail) is portable; the "v2 must demonstrably straddle" half is not. Consider making pace adaptive (retry faster until a straddle occurs) or demoting the v2-straddle check to a logged skip — otherwise this is the most likely CI/other-machine flake in the change.

2. `engine/natsio/driver_test.go:768,793` — the measurement and flush loops in `TestBatchAppliedLagBoundary` drain intents but never `e.EnqueueIntent` them (the warm-up loop at :671-674 does). "Complete-application lag" is therefore notional — appliedTick is the tick the intent *would* apply at, and the engine runs uncontrolled for all 300 measured ticks. That's fine for what the test pins (drain-boundary timing, which is all batching changes), but it diverges silently from the "production-like" framing in the doc comment and from the warm-up phase. One comment line saying application is deliberately notional (drain tick + 1) would prevent a future reader "fixing" it and perturbing the fixed cadence.

**Nits**

3. `engine/natsio/driver_test.go:430,439` — `strconv.ParseUint` errors ignored in the tap; a missing/garbled `tick`/`applied_tick` header silently becomes 0, inflating (obs) or deflating (ack, via the `u > prevAppl` guard — dropped sample) in ways that skew the comparative percentiles. A `t.Errorf` on parse failure is one line.

4. `engine/natsio/bench_intent_test.go:326-329` — `msgs/tick` is reported as an assumed constant (`n` or `controllers`), not a measured count. For batched it's backed by the `IntentBatchStats` assertion at :346-356; for v2 nothing pins it. Harmless as a label; just noting it isn't a measurement.

No new published subject, so no ADR needed per the contract rule — confirm that's the intended reading (it slightly grows the public API for a test-only consumer, same pattern as `Bus.BufferedIntents`).

**Checked and clean**

- `Bus.DrainIntents` (bus.go:360) preserves arrival order and delivers every buffered intent without per-vehicle dedup, and `Contract.DrainIntents` (contract.go:733) appends in that order with held re-issues appended after — so the boundary test's FIFO attribution (`driver_test.go:728-757`) is sound, including drains that contain the tail of one response and the head of the next.
- Bench tick accounting: warm-up runs once per sub-benchmark invocation and `bus` is recreated per invocation, so `allTicks = warmupTicks + b.N*measTicks` (bench_intent_test.go:347) matches `IntentBatchStats` exactly across `b.N` reruns.
- The in-place tick patch on the reused `nats.Msg` (bench_intent_test.go:245) is race-free: each controller patches only its own message, ticks are serialized by `wg.Wait`, and nats.go copies payload into the outbound buffer before `PublishMsg` returns.
- Determinism discipline: the only map iterations in the new code (`touched` in `attribute`, tap state) are test-local and order-insensitive; hold-last iteration in the production drain path remains sorted. No wall-clock or RNG enters any sampled/recorded path — new wall-clock use is confined to test pacing, which the tests themselves acknowledge and control via absolute deadlines with overrun reporting.
- `tsibTickOff` refactor (tsib.go:76,885) is byte-identical to the previous literal `8`; the deliberate literal re-pin in `driver_test.go:411-415` (external-consumer view of the wire format) is a good pattern, not duplication to fix.
- The `lagTap` single-wildcard-subscription design is correct: obs(u) necessarily reaches the broker before the driver's response to it, so within one subscription the obs→intent ordering the v2 pairing relies on is sound; the ±1 residual is honestly absorbed by the +1 tolerance.
- `m.Data[lagTickOff:]` (driver_test.go:434) cannot go out of bounds for real TSIB frames (24-byte header minimum), and batch-mode route updates ride headerless v2 so they hit the else branch as intended.
- BENCHMARKS.md / KB flag-back is doc-only and consistent with what the tests actually pin (I did not re-verify the measured numbers).
