## Findings

**should-fix** — `engine/cmd/demosrv/supervisor.go:140-166`: `start()` now holds `s.mu` across `waitReady` + `waitIdentity` — up to ~720 s (60 s port + 660 s identity) on the big nets this change explicitly targets (la-lean ~400 s world build). `status()` (supervisor.go:212) and `stop()` (supervisor.go:186) take the same mutex, so during a city-scale start the menu's 3-second `/api/status` polls all hang (stacking HTTP handlers and exhausting the browser's per-host connection pool), and `/api/demo/stop` cannot interrupt a wrong start until timeout. Pre-change the hold was ≤10 s, so this is a new liveness property, not a pre-existing one. Related: the start POST for la-lean (~400 s server-side) outlives Chrome's ~300 s response-header timeout, so the client sees a network error while the child keeps starting — recoverable via status polling, but only once the mutex frees. Consider waiting outside the lock (mark active, release, re-check identity under the lock at the end) or at least serving `status()` from a snapshot that doesn't contend.

**should-fix** — `engine/cmd/demosrv/identity_test.go:20-25`: imports `nats.go` and `nats-server/v2` directly inside `cmd/demosrv`, breaching the repo's own confinement rule (CLAUDE.md / ADR-0006: the two NATS modules are confined to `engine/natsio/`; `engine/natsio/probe.go:11-13` states the boundary explicitly — "cmd/* never touches nats.go directly"). The ws-broker + put-run-meta helpers belong in `natsio` alongside `NewTestServer`, exported for the demosrv tests.

**nit** — `engine/natsio/probe.go:31-40`: `ProbeRunMeta` opens a fresh WebSocket connection + JetStream context every second for up to 660 probes against a broker mid-world-build. Works, but a kept connection or backoff (1 s → 5 s) would be gentler and shrink log noise on the child side.

**nit** — `engine/cmd/demosrv/main.go:329` / `replay.go:134` vs `viz/src/demos-core.ts:62-66`: Go emits `&ws=ws://127.0.0.1:8443` raw while the TS side emits `encodeURIComponent(ws)`. Semantically identical after query parsing, but the "same shape … they must agree" comment (main.go:324) is no longer true as strings; if anything ever compares URLs textually it will break. Either encode on the Go side or soften the comment.

**nit** — `engine/natsio/bus.go:339`: `onSignalRequest` calls `b.nc.Flush()` on the subscription callback goroutine, briefly blocking dispatch of subsequent requests on that connection. Harmless at one-viz scale; drop the Flush or note why it's needed.

**question** — `viz/src/nats-client.ts:76-84`: on the early `break` after collecting the full chunk set, does nats.ws's `requestMany` iterator actually tear down the inbox subscription, or does it linger until the 10 s `maxWait`? If it lingers, each pull leaks a subscription for the window — bounded and small, just worth confirming against the nats.ws version pinned.

**question** — `engine/natsio/probe.go:52-57`: the ±5 s `CreatedUnix` tolerance plus static demos.json run ids means a foreign *concurrent* start of the same id still false-passes (documented, nonce deferred). Fine today given single-machine demosrv — flagging only so the deferral is a decision, not an oversight; the probe.go comment already records it, so no action needed.

Everything else checked clean: the netCache lock and double-stat are intact (geojson.go:97-102); part-URL parsing can't traverse (registry-gated ids, numeric index); manifest-last write ordering plus hash+schema-pinned 404s preserve per-fetch atomicity; the accumulator never half-swaps a table and treats tick as non-identity (paused-replay safe); `withSigTick` copies before patching so cached chunks stay immutable across the request-responder goroutine; replay children also get the overridden `-ws` (main.go:137); and the navy theme is pinned byte-for-byte so the default look is provably unchanged.
