The core equivalence argument for the bucketed `boundaries()` holds up under scrutiny:

- The `past` map is keyed by `*Lane` but **never ranged** — only indexed, appended, and deleted — so pointer-keyed map nondeterminism can't leak (engine/engine.go:818).
- Re-append condition `next.Index < i && v.S > next.Length` (engine.go:845) exactly reproduces the old descending sweep's re-scan: strictly-lower index ⇒ bucket not yet visited/deleted; equal or higher index ⇒ old sweep had already passed that lane, so the crosser waited a tick in both versions. Boundary condition (`>` vs `<=`) matches the old guard.
- The stale-entry guard `v.Lane != lane || v.S <= lane.Length` (engine.go:834) preserves the old inner-loop semantics for anything the bucket snapshot got wrong.
- Order-independence claims check out: `pickSuccessor` is pure per vehicle, `routeTable` memoization is order-independent (deterministic per key regardless of first-call order — routing.go:56), Stats counters commute, compaction runs post-loop and preserves `e.order` relative order.
- The new `Lane.Index == i` construction invariant in `NewEngine` (engine.go:786) is the right defensive move since the bucketing routes by `next.Index` where the old sweep used slice position.
- `totalLaneKm` cache: fixed slice order ⇒ bit-identical sum; both callers are tick-path; `Length` immutability documented at the field (network.go:13). Sound.
- No NATS subject/payload changes; metview is a read-only consumer of the file-sink schema with the drift risk documented in-code; KB updated in-diff. CRC-identical 7200-tick stress run is the right empirical backstop.
