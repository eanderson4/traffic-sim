  Scope checked: the staged diff, against kernel M1 semantics (`engine/sigctl.go`, `engine/signal.go`), the contract plane (`engine/natsio/contract.go`, `run.go`, `verb.go`), and `scripts/whatif.py`.   ### Blockers
  None by the repo's bar (no sim-state, determinism, replay, or record-plane defect reachable in normal operation; the kernel is untouched).

  ### Should-fix

  1. **`applied := tick + 1` is a scheduling assumption nothing guarantees** — `engine/natsio/sigctl/sigctl.go:670`. The run loop is explicit: "Never a barrier on controller input" (`engine/natsio/run.go:281-283`), and `contract.go:494-501` spells out that at `PaceFloor == 0` tick time outruns any client's wall-clock reaction — which is exactly the bracket's mode (`-pace 0` in `sigctl-bracket.py:58`). A verb reacting to snapshot tick T applies at whatever `e.Tick` the next control drain lands on, ≥ T+1 and load-dependent. All self-tracking (`holdUntil`, `chainStart`, `phaseSince`) inherits the skew: predicted `holdUntil` ends *before* the actual hold, so `estimated()` falls back to the fixed-time derivation while the kernel still holds the controller's phase — and the uncontested branch (sigctl.go:333-334) then issues a verb commanding the *fixed-time* phase, superseding its own live hold. It self-corrects, but the ADR addendum's claim — self-tracking "is exact while the controller is the only commander" — is missing its real precondition: next-boundary application. The reply carries no applied tick, so the skew is undetectable client-side. Minimum: state the precondition in the ADR note and the package doc. Better (and already PROPOSED in the same addendum): an applied-tick/effective-hold field in `VerbReply` — this client is the argument for building it.

  2. **Chain-contiguity boundary mismatch with the kernel** — `sigctl.go:679` (and the counter twin at :672). Kernel renews the chain iff `last.until >= e.Tick` (`engine/sigctl.go:291`); the controller starts a new chain iff `applied >= ps.holdUntil`. At `applied == holdUntil` exactly, the kernel *continues* the chain while the controller believes a fresh one started — predicted decline moves later than the real one, and the controller issues exactly the doomed renewal the design says it never sends (kernel records hold 0 + lapse). Unreachable with the shipped defaults (hold 100 / cadence 20 / renew-below 30 renews at remaining 21), but reachable via the controller's own documented flags (`-hold`, `-cadence`, `-renew-below` on cmd/sigctl, e.g. hold 100 + renew-below 20). One-char fix: `applied > ps.holdUntil`. Record-and-defer is defensible per the triage bar; the fix is cheaper than the record.

  3. **Detector grid silently misses detectors for `-detect-radius > 50`** — cells are hardcoded 50 m (`sigctl.go:551`, `:632`) and the neighborhood scan is ±1 cell, which is complete only for radius ≤ 50 m. `-detect-radius` is a user-facing flag with no bound; at 75 m, detectors two cells away are never counted → phantom gap-outs. Derive the neighborhood from the radius or clamp/reject radius > 50.
