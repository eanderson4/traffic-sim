## Findings

**Blockers** — none.

**Should-fix**

1. `deploy/README.md:117-118` — "re-running this rotates the token … and invalidates the old one" is wrong, dangerously so for the emergency-rotation case. The token reaches demosrv via `secretKeyRef` env, captured at container start: after re-running step 2, the **old** token keeps working and the **new** one is inert until the next pod restart (up to ~6 h away via the CronJob). An operator rotating a leaked token would believe it dead while it stays valid. Add "then `kubectl rollout restart deployment/demosrv -n traffic-sim`" to the step.

**Nits**

2. `deploy/README.md:110` — `TAG=v0.1.0-$(git rev-parse --short HEAD)` is commit-unique, not build-unique; rebuilding from a dirty tree at the same HEAD re-pushes over a referenced tag — exactly the stale-image hazard the adjacent comment (line 108-109) warns about. A `-$(date +%s)` suffix closes it.
3. `deploy/k8s/cronjob.yaml:397` — the CronJob is the *only* automatic run-freshness mechanism and fails invisibly if `registry.k8s.io/kubectl:v1.35.5` doesn't pull (that repo only publishes some tags/arches); verify the tag pulls in-cluster once before relying on the 6 h cadence.
4. `deploy/k8s/cronjob.yaml:379-381` — "always recycled before its run can complete" silently depends on serve's default `-pace 1` (realtime) and dt = 0.1 s (360000 ticks = 10 h); demosrv doesn't pin `-pace` (main.go:290). True today; worth one clause in the comment naming the assumption.

**Questions**

5. `deploy/k8s/deployment.yaml:446-459` — initContainer auth assumes the node SA is reachable via metadata (README: bucket IAM on the default compute SA). If `carbon-dev` has Workload Identity / metadata concealment enabled, an unannotated KSA can't act as the node SA and the pull fails at first rollout. README implies setup was exercised 2026-07-25 — confirm the pull actually ran on this cluster, not just the IAM grant.
