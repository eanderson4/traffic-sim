Findings, in triage order.

**should-fix — KB entry overclaims the fix; the registry-first readiness race survives it.** `docs/kb/articles/cross-topic-concerns.md` (diff line 10) now says "(b) FIXED 2026-08-05: the constructors now `nc.Flush()` before returning, so responders are registered server-side before any client can address them." That last clause is not true for the readiness path the shared harness actually uses: `RunLive` starts the registry at `engine/natsio/run.go:157` *before* constructing the bus and contract at `run.go:173`/`run.go:179`, and `startLiveRun` (`engine/natsio/contract_test.go:56`) treats registry-meta visibility as "the run is up" and lets tests fire hellos immediately. A hello landing in the window between `reg.Start` and the contract flush still fast-fails `no responders` — and that window contains `NewRecorder`'s JetStream stream creation, which is exactly what stretches under runner load. The flush genuinely fixes the SUB-propagation half of the race (constructor return now implies server-side registration), but the KB should scope the claim to that, and keep the registry-before-responders ordering recorded as open (or reorder `reg.Start` after contract construction — a behavior change to the abort path, so a decision, not a drive-by). The prior round's archived sol review (in this same diff) flagged precisely this ordering; marking the whole item FIXED buries it.

**nit — double flush in `NewBus`.** `engine/natsio/bus.go:243` flushes again right after `NewPublishBus` already flushed at `bus.go:295`, so live-run construction pays two sync RTTs where one (after the intent subscribe) covers both. Harmless on an embedded server; not worth restructuring the layering over.

**nit — error-path asymmetry.** `bus.go:296` cleans up with `sub.Unsubscribe()` while the same failure in `NewBus` (`bus.go:244`) and `NewContract` (`engine/natsio/contract.go:395`) use `Close()`. Equivalent today (`Bus.Close` is just the two unsubscribes, nil-safe); will drift if `Bus` ever grows owned resources. `b.Close()` would be uniform.

Checks that came back clean:
- **Correctness of the fix itself:** `Flush()` sends PING after the already-queued SUBs and waits for PONG, so the server has processed the SUBs before the constructor returns — the right primitive for this race on a single embedded server (clustered interest-propagation caveats don't apply per ADR-0004 local-first). Failure paths unwind correctly (`Bus.Close`/`Contract.Close` are nil-safe and unsubscribe everything bound so far).
- **Determinism:** constructors run once, outside the tick loop; the added RTT touches no simulated state, no RNG, no float accumulation, no map iteration in a sampled path.
- **Contract:** no subjects or payloads change; this strengthens a readiness guarantee without altering the wire. No ADR required; the KB update in the same commit satisfies the keep-KB-current rule (modulo the wording above). The `nats.go` usage stays confined to `engine/natsio/` per ADR-0006.
- **Review archives:** the two archived rounds document the prior `driver_test.go` and `ci.yml` commits — docs-plane content, consistent with the ADR-0013 archive policy (no `*-reviewed.patch` committed).

**question** — the KB says the per-test `nc.Flush()` workarounds are "redundant but harmless." The ones that flushed the *client's own* connection after constructing a client-side subscriber were never the same race as this fix (engine-side constructors); if any test's flush was actually masking the registry-first window above, deleting it later on the strength of this KB line would resurrect the flake. Worth knowing which kind each is before anyone cleans them up.
