## Findings

**Should-fix — serve's recording store lands on the node boot disk, unbounded, and the emptyDir comment claims otherwise.** `deploy/k8s/deployment.yaml:518` says the 12Gi `sizeLimit` bounds things "so a runaway cache can't eat the node's 100 GB boot disk" — but the pod's largest disk writer isn't on the emptyDir. serve *always* runs the JetStream recorder (`natsio.RunLive(..., RecorderConfig{})`, `engine/cmd/serve/main.go:320`): FileStorage, `MaxAge` 0 = keep everything (`engine/natsio/recorder.go:96-103`), keyframes every 100 ticks. Over a 360000-tick run at capacity 50000 that's ~3600 keyframes at up to ~1.2 MB each — multiple GB per 6h window — written to `os.MkdirTemp("", ...)` → `/tmp` on the container's writable layer (`serve/main.go:577`). The pod sets no ephemeral-storage requests/limits, so the failure mode is unmanaged node disk-pressure eviction, not the bounded eviction the comment promises. One-line fix: set `TMPDIR=/data/tmp` in the Deployment env (children inherit demosrv's env) plus a `mkdir -p` in the initContainer — then revisit whether 12Gi still fits 5 GB data + geojson scratch + the store — or add ephemeral-storage limits.

**Should-fix — initContainer copy is not restart-safe.** `deploy/k8s/deployment.yaml:51`: the emptyDir persists across initContainer retries within a pod, and `gcloud storage cp -r gs://…/scenarios /data/` into an existing `/data/scenarios` nests a second copy at `/data/scenarios/scenarios/` (gsutil-inherited semantics), doubling usage toward the 12Gi limit. Worse, a partially-copied first attempt leaves `<city>-lean` dirs that pass demosrv's existence stat-check (`registry.go:209-222`) but are missing files, failing later and murkier. Prepend `rm -rf /data/scenarios` or use `gcloud storage rsync -r`.

**Nit — BackendConfig health checks omit `type: HTTP`** (`deploy/k8s/backendconfig.yaml:14,23`). GKE's default fills it in, but the ws-side `/healthz` precondition is already the delicate part of go-live; being explicit removes one inference.

**Question — does `registry.k8s.io/kubectl:v1.35.5` actually pull?** (`deploy/k8s/cronjob.yaml:394`). Worth one manual pull before relying on it: an ImagePullBackOff here is silent, and the site then quietly idles after the 10-sim-hour horizon — exactly the failure the CronJob exists to prevent, with `/api/status` liveness staying green throughout (documented in `deploy/README.md:151-155`, but that mitigation assumes the CronJob itself is healthy).
