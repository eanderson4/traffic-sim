## Findings

**should-fix — completion watermark is satisfiable by pre-sentinel backlog, so it doesn't guarantee what its comment claims** (`engine/natsio/driver_test.go:1180`, `:1228`)
`sentMark` is captured before the sentinel obs is published, but at that moment the driver can still hold a backlog of unprocessed warm-up obs (the existing quiescence comment itself says fleet-scale responses take many ms and backlog builds). Every backlogged response's intents land *after* `sentMark` and count toward `SentIntents()-sentMark`. Loop order makes it worse: the `LastObsTick >= lastObs` loop (line 1217) exits only once the driver has *started* the sentinel — and since `onObs` is sequential, that means all backlog responses are already fully published — so on entry to the watermark loop the delta already includes the whole backlog. If backlog ≥ `vehicles` (plausible at the 5,000-vehicle leg, where late warm-up responses are each ≈`vehicles` intents), the watermark passes immediately with the sentinel still mid-compute. That is exactly the >50 ms-compute false-pass window this change claims to close; protection degenerates back to Phase B's 50 ms heuristic precisely at the scale where the hole exists. It can't cause a false *failure* (the sentinel response is eventually exactly `vehicles` intents, so the 30 s loop terminates), so this is a weakened-guard/overstated-comment issue, not a blocker. Minimal sound fix: run a drain-down pass (fresh==0 and `LastObsTick` ≥ last *warm-up* obs, plus a short publish-quiet check) *before* publishing the sentinel, so `sentMark` is taken against an idle driver; alternatively expose a driver-side completed-obs watermark stamped after `onObs` returns.

`lastObs := int64(e.Tick) // last warm-up AfterStep's obs` — after this change the tick is the sentinel obs, not a warm-up obs. The Fatalf at line 1230 has the same wording.
