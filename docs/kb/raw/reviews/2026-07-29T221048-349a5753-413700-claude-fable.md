**Should-fix**

1. `engine/natsio/recorder.go:389` — `logIntentBatch`'s `flush` reuses the batch buffer (`buf[:0]`) while earlier TSLB messages of the same tick are still in flight (pubacks awaited only at `awaitBatch`, recorder.go:207). This is safe today only by an undocumented accident of nats.go v1.52.0: `PublishMsgAsync` zero-values `pubOpts` (js.go:1012), so `maxRetries` is 0 — but the library retains `paf.msg`, whose `Data` is this exact slice, and *resends it* on a no-responders reply whenever retries are enabled (js.go:915–933; sync `PublishMsg` already defaults to 2 retries, js.go:535). One `nats.RetryAttempts` option added to `publish` later — a natural resilience tweak — makes this silent record corruption: split batches are near-uniform in size, so a resend of the mutated buffer can be a byte-valid TSLB batch (batch k duplicated, batch k−1 gone), and replay diverges with every strictness check in `DecodeTSLB` passing. On the plane whose own comments say corruption is unrecoverable, either allocate a fresh buffer per flush (one alloc per message — noise next to a JetStream publish) or pin the invariant with a comment at the reuse site.

2. `engine/natsio/tslb.go:99` — `make([]engine.TickedIntent, 0, count)` preallocates from the untrusted u32 header before validating a single record byte. A corrupt count of ~4.29e9 requests a ~0.5 TB allocation and kills the reader, where every other malformed input gets the decoder's deliberate loud error. Cap it: `count > len(rest)/61` (61 B = the minimum record: 18-byte prefix + 43 fixed) is already an error the loop would eventually hit; checking it first keeps the prealloc bounded.
