**Blockers**
- **Scenario demand is validated and hashed but never executed.** `Load` reads demand parts (`engine/scenario/scenario.go:172`), but `RunSpec` materializes only the built-in spawner (`engine/scenario/scenario.go:246`). `simrun` immediately calls `engine.Run` (`engine/cmd/simrun/main.go:77`), and `serve` starts only the default vehicle driver, not a demand director. Therefore a valid demand-only scenario—explicitly tested at `engine/scenario/scenario_test.go:264`—runs with zero demand. This contradicts ADR-0012’s statement that a demand file is runtime director configuration (`docs/kb/decisions/ADR-0012-scenario-format.md:73`) and makes the hash cover inputs the run did not consume.
- **`-ticks` breaks the declared `(content-hash, seed)` identity.** `ticks` is hashed as part of the canonical manifest (`engine/scenario/scenario.go:51`, `engine/scenario/scenario.go:140`), but both CLIs replace the effective tick budget without changing the hash (`engine/cmd/serve/main.go:90`, `engine/cmd/simrun/main.go:48`). Two runs can consequently have identical `(hash, seed)` but different horizons and outputs. Conversely, the authored seed is already inside the hash (`engine/scenario/scenario.go:50`) and is then repeated as the second identity component. The ADR must distinguish content fields from sweep/execution parameters before this identity is recorded durably.
- **The “strict YAML” fence permits silent scalar coercion.** `rejectNonStrict` accepts `!!int`, `!!float`, `!!bool`, and `!!null` irrespective of the destination field (`engine/scenario/scenario.go:443`), after which yaml.v3 performs typed coercions (`engine/scenario/scenario.go:419`). Examples include `format_version: 1.9` truncating into an integer, `ticks: 1.9` becoming `1`, and `id: true` becoming the string `"true"`. This directly defeats the ADR’s explicit-quotation/Norway fence (`docs/kb/decisions/ADR-0012-scenario-format.md:51`). The fence needs schema-aware node-type checking before unmarshalling.
- **Non-finite floats pass validation.** Comparisons such as `dt < 0`, `veh_per_h <= 0`, and `weight <= 0` do not reject NaN (`engine/scenario/scenario.go:332`, `engine/scenario/scenario.go:372`, `engine/scenario/scenario.go:391`); infinities also generally pass. A `.nan` `dt` reaches `RunSpec` because NaN is not equal to zero (`engine/scenario/scenario.go:254`). Every numeric field needs `math.IsNaN`/`math.IsInf` rejection plus bounded domain checks.
- **Vehicle-type sampling still depends on Go map iteration.** `pickType` computes `tot` while ranging over the map, then sorts only for cumulative selection (`engine/cmd/demand-director/main.go:132`). Floating-point addition is non-associative, so three or more weights can produce different totals and decisions across processes. This violates ADR-0005 and the function’s own “map order is forbidden” comment at `engine/cmd/demand-director/main.go:124`.
- **Flow identity is fundamentally incompatible with overlays and CRN comparisons.** `Flow` has no durable ID (`engine/scenario/scenario.go:88`); RNG identity uses origin plus only the low byte of the positional index (`engine/cmd/demand-director/main.go:67`), while request IDs also use that index (`engine/cmd/demand-director/main.go:265`). Reordering or inserting a flow changes every subsequent realization; indices 0 and 256 collide for the same origin; independently launched demand files restart indices and can emit duplicate request IDs. A stable, required flow ID—namespaced by materialized scenario/part—is needed before additive overlays.

**Should-Fix**
- **Path confinement is lexical, not physical.** `resolvePart` rejects `..` and absolute strings but follows symlinks outside the scenario directory (`engine/scenario/scenario.go:305`). `fmt` can therefore rewrite an external YAML target (`engine/scenario/scenario.go:293`), and the hash can depend on mutable external content. Resolve the root and target through symlinks and verify containment, or explicitly forbid symlinked parts.
- **The hash is not a versioned canonicalization protocol.** Hash bytes depend directly on yaml.v3’s map sorter and float encoder (`engine/scenario/scenario.go:459`), with no algorithm/version domain separator. A yaml.v3 or Go formatting change can invalidate old recording bindings. Existing tests compare hashes only within the same binary (`engine/scenario/scenario_test.go:112`); add fixed golden vectors and encode a canonicalization/hash version.
- **Only some YAML is canonicalized.** Network, control, and metrics parts are hashed byte-for-byte (`engine/scenario/scenario.go:166`, `engine/scenario/scenario.go:184`), so whitespace/comments in future control or metrics YAML change identity even though `scenario fmt` claims semantic diffs and hash stability. This must be resolved before the observability ADR: either typed canonicalize every authored YAML part or explicitly define hashes as artifact-byte identity rather than semantic identity.
- **Path framing and normalization are under-specified.** Hashing uses `path + NUL + data + NUL` without lengths or a hash-domain prefix (`engine/scenario/scenario.go:271`). Use length-prefixing and normalized `/` relative paths. Also decide whether `./network.json` and `network.json` are the same content identity and how Windows separators/case behavior are handled.
- **The implicit default vehicle type is not cross-validated.** Empty `vtypes` means the director chooses `"car"` (`engine/cmd/demand-director/main.go:128`), but full scenario validation checks only explicitly named map entries (`engine/scenario/scenario.go:391`). A scenario with `types: [truck]` and no `vtypes` loads successfully, then emits rejected `car` verbs.
- **Type normalization is ineffective and duplicates are accepted.** The trim at `engine/scenario/scenario.go:338` modifies only the loop variable, not `m.Types`; `" car "` passes validation and later fails registry lookup. Duplicate type names can also alter built-in spawner weighting. Either reject non-canonical whitespace/duplicates or rewrite the slice deterministically.
- **Piecewise demand semantics are incorrect.** The first Poisson arrival is always at `t=0`, because the gap is sampled after selecting the current arrival (`engine/cmd/demand-director/main.go:111`). A gap calculated under one slice can jump through later slices (`engine/cmd/demand-director/main.go:120`), and the initial `ok` result is discarded (`engine/cmd/demand-director/main.go:239`), allowing all-zero sliced flows to attempt an empty, underflow-numbered spawn. This contradicts the advertised Poisson-gap and piecewise-rate model.
- **`RunSpec.Hash` is a NATS payload-schema change.** It is embedded in public registry metadata (`engine/natsio/registry.go:27`) while the registry schema version remains unchanged. ADR-0012 says both that the registry gains the field and that “nothing on the NATS contract changes” (`docs/kb/decisions/ADR-0012-scenario-format.md:179`). Per `AGENTS.md:18`, this needs an explicit migration/compatibility note and a documented `scenario_hash` field in the AsyncAPI schema, not an opaque additive Go field.
- **`-scenario` ownership is inconsistently enforced.** Only `-netfile` conflicts; explicit `-rate`, `-density`, `-types`, and `-net` are silently ignored (`engine/cmd/serve/main.go:52`, `engine/cmd/simrun/main.go:32`). Reject scenario-owned flags when `-scenario` is present, except for deliberately supported sweep overrides.
- **Formatting is non-atomic.** `Format` writes the manifest first and demand files sequentially (`engine/scenario/scenario.go:290`), so a later failure leaves a partially formatted directory. Stage temporary files and rename after every encode/write succeeds.

**Questions Requiring ADR Clarification**
- Are `seed` and `ticks` scenario content, run parameters, or defaults? The current format treats each as all three.
- Must hashes identify exact source artifacts or semantically equivalent materialized scenarios? Raw control/metrics/network hashing currently chooses the former; ADR wording promises the latter.
- How are flow IDs, entity namespaces, overlay patch order, duplicate part references, and collisions between added parts defined?
- Will observability tooling need both the authored scenario hash and a separate materialized/effective-run hash after overlays and CLI overrides?

**Load-Bearing Positives**
- Unknown fields, aliases, custom tags, duplicate YAML keys, multiple documents, unsupported versions, origin references, and overlapping slices are correctly treated fail-loud.
- Canonical struct-field order and yaml.v3’s sorted map output provide deterministic output within the currently pinned library version.
- Keeping the scenario hash outside CRC’d world state is the right separation; binding it through registry/recording metadata is the right architectural location once identity semantics are fixed.
