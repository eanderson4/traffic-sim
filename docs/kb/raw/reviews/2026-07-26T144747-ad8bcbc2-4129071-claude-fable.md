## Review: ADR-0026 M0 baseline benchmark (bench_intent_test.go + BENCHMARKS.md §(d))

Verified against the natsio sources: all referenced internals exist and behave as the benchmark assumes — `intentSubjectTokens=5` matches `SubjectCtlIntent` (bus.go:53, server.go:98); the nil-recorder claim is sound (`c.rec` is consumed only by `emitPause` at contract.go:1032, reachable only via `AfterStep`/pause paths the bench never runs); `Vehicles()` is a deterministic slice (engine.go:288); `DrainIntents` hold-last can't fire when every vehicle gets a fresh intent (contract.go:784), so the `Held` assert is a real tripwire; percentile math is correct nearest-rank (p99 of 100 = 2nd-highest); the doc's arithmetic all checks out (2.27/2.88/3.13M, 61 ns → ~16M/s ceiling, 9 ms ≈ 9%). No shipped-path code changes, no subject/payload changes, no determinism exposure — wall clock and goroutines are confined to the benchmark. Could not compile-verify (`go vet`/`go test` denied by the sandbox); verification is by source cross-reference only.

**Blockers:** none.

**Should-fix**

1. `engine/natsio/bench_intent_test.go:320-332` — `BenchmarkOnIntentCPU` never asserts the messages were actually buffered. If subject shape, `intentSubjectTokens`, or `DecodeIntent` ever drifts (M1 adds header demux to `onIntent` — this exact code path churns next milestone), the loop silently measures the early-return drop path and reports a bogus "onIntent CPU" number that M1/M3 would then be compared against. One line after the loop — assert `bus.dropped == 0` (or `len(bus.buf) > 0`) — makes the baseline self-checking. `BenchmarkIntentIngest` has this protection (`drained == n`); the CPU bench doesn't.

2. `engine/BENCHMARKS.md:107-108` — "ingest+drain is the correct comparison scope for M3 (pinned by ADR-0026)" overstates. ADR-0026 M3 (ADR-0026-batched-intents.md:238-244) pins **applied-lag (source obs tick → `applied_tick`) p50/p99 no worse than baseline** as a first-class acceptance metric, and this M0 baseline cannot produce it (no obs plane, stops before apply). That's defensible — the v2-mode applied-lag baseline can come from M3's own paired v2/TSIB rerun — but the doc should say that explicitly rather than implying §(d) is the complete M3 baseline. One sentence.

**Nits**

3. `engine/BENCHMARKS.md:109` — "`b.N=1`" is only true under the documented `-benchtime=1x` invocation; without it the harness scales b.N and each iteration is another 100 ticks (results stay valid — percentiles pool over `b.N*100` samples — just slow). Also `bench_intent_test.go:197` under-capacities `tickTotals` in that case. Harmless.

4. `engine/natsio/bench_intent_test.go:119` — on the "hello never reached the contract request buffer" failure path, the `conn.Request` goroutine is abandoned mid-flight. Failure-path only; fine at this stage.

**Questions**

5. §(d) attributes the super-linear `DrainIntents` growth to the hold-last sort — correct (contract.go:777-782 sorts all n tracked ids every drain even when all are fresh), and that's a real production run-loop cost the bench just surfaced, not a bench artifact. Worth a KB/deferred-work note as a possible TSIB-era optimization (skip the sort when `len(fresh) == len(hold)`), per the repo's record-should-fixes convention?
