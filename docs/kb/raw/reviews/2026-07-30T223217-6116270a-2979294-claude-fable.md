Review of the staged ADR-0036 diff. I read the full patch and the surrounding engine code (`routing.go`, `keyframe.go`, `engine.go` sweep, `gridlock.go`, `mobil.go`). The flag-off path is genuinely inert (every new mechanism is gated, keyframe stays ≤v5, weights fall back to `freeFlowTime`), determinism hygiene is good (no map iteration feeds decisions; `routeEpochs`/`staticTabs` are keyed-access only; budget is consumed in the deterministic sweep order; relaxation runs in fixed lane order), and the v6 writer/reader gating is symmetric with loud mismatch rejection. The two findings below both attack the diff's central replay claim — "every table is a pure function of (frozen weights, network)" — which is the property `TestAdaptiveRestoreIsCRCExact` exists to pin.

## Blocker

**1. First-use table builds skip hysteresis, so a restored engine can build a different table than the live engine served — mid-run restore diverges in exactly the marginal-poison band the tests document.**
`engine/routing.go:215` — the first-use path runs raw `routeDijkstra(destIdx, e.routeWeight)`, while a stale recompute goes through `rerouteTable` (`routing.go:210`), which reconciles against the static table under the max(30 s, 15%) margin. These produce different tables whenever the adaptive path is better than static *but within the margin*: raw Dijkstra takes the adaptive hop, `rerouteTable` keeps the static one. After a mid-run restore, `routeTabs` is empty (derived state), so every table is rebuilt via the un-reconciled first-use path — the restored engine diverts where the live engine held. Your own test comment constructs this band precisely: one capped crawler sample lifts c_0 to ~48 s, "deliberately NOT enough to beat hysteresis" (`engine/adaptive_test.go:233-236`) — restore in that state and the warm engine's fresh build picks b_0 while the live engine serves c_0. The existing restore tests only exercise poison that is either negligible or far past the margin, so they can't see it. Fix is small: when the flag is on, route the first-use build through `rerouteTable` too (the "unmetered" property is about the budget, not about skipping reconciliation).

**2. Stale-past-budget tables are functions of the *previous* epoch's `ttSnap`, which the keyframe does not carry — restore diverges during any budget-starved window.**
`engine/routing.go:206-207` serves the cached table when `rerouteBudget <= 0`; that table was built from the prior epoch's frozen weights, which `Step` overwrites in place at rollover (`engine/engine.go`, the `e.ttSnap[l.Index] = l.ttEMA` loop). The keyframe stores only the current `ttSnap` (`engine/keyframe.go` v6 lane section), and `routeTabs`/`routeEpochs` are declared derived. So if a keyframe lands while any destination's table is stale past budget, the restored engine's first-use rebuild (from *current* `ttSnap`, unmetered) differs from the stale table the live engine is still serving — CRC divergence. This isn't a corner case at target scale: at each rollover *every* cached table goes stale simultaneously, so with D active destinations and budget 4 the divergent window is ~⌈D/4⌉ ticks of every 600-tick epoch; on chi-loop-urban with hundreds of route destinations that's a large fraction of all restore points. The tests never exceed the budget across a restore (≤2 destinations), so `TestAdaptiveRestoreIsCRCExact` passes while the property fails in general. Fix needs a design decision, e.g.: keyframe `routeEpochs` plus a `ttSnapPrev` array (2 more f64/lane) and rebuild stale tables from the previous snapshot; or make recompute scheduling access-independent (fixed round-robin cursor over destinations, cursor keyframed); or — cheapest — have restore mark rebuilt tables with the epoch they'd have had live. At minimum the ADR's Replay paragraph (ADR-0036 "a MID-RUN restore continues bit-exactly") must be scoped to "when no table is stale past budget," but that scoping guts the guarantee, so I'd fix rather than re-word.

## Should-fix

**3. ADR cost/metering claims are slightly off.** ADR-0036 "Consequences": "≤ 4 Dijkstras per tick worst case" — a budgeted recompute may also build its static reference (`staticRouteTable`, `routing.go:234`, one extra Dijkstra on first hysteresis use), and first-use builds are explicitly unmetered and unbounded per tick (a demand wave introducing many new destinations pays them all in one tick — pre-existing behavior, but the ADR presents 4 as the worst case). Also "one int64 per vehicle" — `laneEntryTick` is u64. Doc-only; fix the ADR text.

## Nit

**4. Scenario can't express `reroute_budget_per_tick: 0`** (`engine/scenario/scenario.go:1242-1244` maps zero to "keep default"), and the engine semantics of an explicit zero budget in `RunSpec` (tables frozen at first-use forever) are undocumented. The `AdaptiveRouting` field has the analogous caveat written down; the budget field doesn't.
