## Findings

**Blockers** — none found. Contract discipline is in order: `ts.{run}.state.sig.req`, `sig_chunk`, the observer-publish amendment, and the 4 MiB `MaxPayload` are all covered by ADR-0016 (ratified) + AsyncAPI 2.3.0; the GeoJSON manifest contract by ADR-0018. Determinism: no map iteration or wall-clock in sampled paths; chunk packing is a pure function of file order; the sigframe refactor is byte-pinned by tests.

**Should-fix**

1. `viz/src/main.ts:145` (requestSig) — after 3 failed pulls, `sigReqRetries` permanently disables the pull path; it re-arms only on a *pull success* or a ws reconnect. For a live run the 20-tick broadcast covers it, but a **paused replay never rebroadcasts the table** (ADR-0016 §5), so a client that eats 3 transient reply timeouts while paused shows no signals until reload/reconnect. A slow re-arm timer (e.g. reset the budget after 60 s) would close it cheaply. Defensible to defer — record it if so.

2. `engine/cmd/demosrv/geojson.go:624` (netKey) — every `/net/{id}.geojson` **and every part request** re-reads and re-hashes the entire network file. For la-lean that's a several-hundred-MB read+SHA256 ×(parts+manifest) per page load, serialized with the client's sequential part fetch. Deliberate per the sol-review note and fine for a dev server, but a (path, mtime, size)→hash memo would remove ~5 large reads per load with no correctness cost. Defer-ok.

**Nits**

3. `engine/cmd/demosrv/supervisor.go:2030` (mirrorStatus) — `/api/status`'s `run` for a replay is the bare recording run (`recrun`), while every live consumer of a replay uses `recrun-replay`. demos.ts happens to ignore it for replays, but the field is now contract-ish surface; suffixing (or documenting) would prevent a future consumer mixing them.

4. `engine/cmd/demosrv/geojson.go:608` (isManifest) — sniffing `"parts"` in the first 4 KiB can false-positive on a single-file doc whose early content contains the literal `"parts"` (e.g. a lane id string). Consequence is only a lost cache (`no-store` on a huge file). Matching `"features":[]` too, or a leading-bytes check, would be tighter.

5. `viz/demos.html:104` — the inline navy/paper palettes duplicate `theme.ts` values by hand; third copy of the palette (after `:root` defaults). Drift risk is acknowledged in comments; noting it so it lands in the KB if a theme edit ever ships.

6. `viz/src/tssg.ts:154` — `parseSigChunkHeader` accepts leading zeros (`01/2`) that the tightened contract pattern `^[1-9][0-9]*/...$` forbids. Lenient-client is fine (the Go publisher can't emit them); mentioning only because the contract pattern was deliberately tightened this round.

**Questions**

7. `engine/cmd/demosrv/supervisor.go:169` — `start()` holds `s.mu` through the up-to-660 s identity wait, so a second start POST (different demo) blocks for the full duration of the first's world build rather than replacing it; only `stop()` can abort. Intended? The status mirror hides the symptom from polling, but the menu's "switch demo while one is building" path serializes behind the build.

8. `engine/natsio/bus.go:2560` (onSignalRequest) — the non-inbox-reply and non-empty-payload log lines are unbounded (unlike the 3-per-run `sigErrs` budget). A misbehaving observer republishing requests could spam stderr. Worth the same first-N cap?

Also verified and fine: the abort-generation scheme has no stale-abort path (gen allocated under mu, abort stamps only the latest); reply confinement to `_INBOX.` closes the reply-subject amplification hole; the reaper closes `a.done` *before* taking `s.mu`, so a child death still aborts a lock-holding `waitIdentity`; `mergeParts` avoids the spread-overflow; cached chunks are immutable (`withSigTick` copies); manifest-last write ordering makes killed generations safe; empty-table and single-chunk back-compat paths are tested on both sides.
