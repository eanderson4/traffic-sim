# External review — staged diff (baked replay pipeline, ADR-0021/0022/0024/0025, Chicago show)

Reviewed via five parallel section passes (engine core, bake CLI, natsio/contract, viz, scripts) over the exact patch; the blocker below I re-verified directly against the patch text.

## Blocker

1. **engine/natsio/bake.go:133–158, 190–205 (patch 12043–12126)** — The record digest double-hashes every tick-group boundary message: a message with `t > next` is `h.add`ed when read, parked in `pending`, then `h.add`ed again when re-consumed by the next group (and the final pending again in the tail drain). `recordHasher.add` (logcursor.go, patch 13714) is a plain `sha256.Write` with no seq dedup — confirmed. The result is deterministic (so the stability test passes) but violates contracts/baked-replay-v1.md's "sha256 over the log messages as consumed, in stream order" — an independent verifier computes a different hash, and the digest feeds the `baked/{run}/{hash12}/` content key. This is exactly the "before anything durable binds the result" window: fix now (skip `h.add` on re-consumption of `pending`), or amend the contract to describe the actual framing; fixing after publication invalidates every published key.
