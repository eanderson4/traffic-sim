Fix direction: per-demo overlay association in `demos.json` (or overlays namespaced by network). Surfaced by Fable, chicago-metro review 2026-07-24.
- **Paced replay / VCR mode (watch a recording sped up)** — replay today is an in-process CRC audit (`ReplayFromStream`) that publishes nothing, and `serve` hardcodes PaceFloor = dt (1× realtime). Two missing pieces: expose PaceFloor as a run parameter (live runs viewable at >1×) and a replay driver that re-simulates from the record while publishing the live plane at a configurable pace (seek keyframe → re-sim + snapshot per tick, no contract plane). The viz already renders any snapshot rate; batch-vs-realtime duality presumes this exists (ADR-0005 §4; congestion-metrics before/after reveal). Surfaced 2026-07-23 code walkthrough.
- **Collision/overlap events on the record plane** — today overlaps are only visible as end-of-run `Stats` counters (simrun's `collisions=` print); nothing on `log.*`, nothing in snapshots, no tick/lane/vehicle-pair attribution, so live-run overlaps are undebuggable and every consumer (viz, drive-demo e2e) must re-derive bumper gaps itself. A per-tick overlap event (tick, vehicle pair, lane/s, signed gap) on the record plane would make them findable and fixable — and because overlaps are deterministic from state, it's a derived signal: replay recomputes it, no replay-semantics impact. Belongs near the ADR-0014 metric kernel (run-quality signal) or as a `log.event` extension. Surfaced 2026-07-23 drive-demo design review (Fable: "no collision signal exists anywhere").
